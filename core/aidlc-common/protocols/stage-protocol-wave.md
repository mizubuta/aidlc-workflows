# Wave Protocol Module

エンジンが `directive.protocol_modules` に `wave` を挙げたとき、すなわち `directive.wave` を伴うユニットごとの設計ステップで、このモジュールを読み込む。

**ユニットごとのバッチウェーブ（任意、stage-major のみ）。** 明示的に選択された stage-major の進行において、functional-design、nfr-requirements、nfr-design、infrastructure-design では、エンジンが修復済みの Bolt-DAG スナップショット 1 つから `directive.wave` を出力することがある。Code Generation は共有ワークスペースに書き込み、Plan Approval で強制停止するため、引き続きウェーブの対象外である。各エントリには、解決済みのユニットローカルな入力/出力、`required_produces`、`unit_memory_path`、`build_required`、`completion_required`、構築対象ユニットの回答済み `questions_file`、そしてレシートに裏付けられた `review_state` / `review_iteration` が含まれる。種別上該当しないユニットと完全に確定済みのユニットは省かれ、大きなバッチは決定的な同一バッチのプレフィックスとして届く。親は `stage_file`、完全な `inline_context_paths`、`context_warnings`、蓄積されたステアリングバンドル、有効な `review_class`、レビュアー設定、センサー、そして親が指すユニットの `memory_path` を保持する。決して `runtime-graph.json` から兄弟エントリを再構成しない。

`directive.wave` が存在する場合は、通常のユニットごとの経路やゲートの経路より先に、それに基づいて分岐する。親のユニットフィールドは最初のエントリの互換性用の射影であり、別個の作業ではない。親の警告は一度だけ表示し、その後すべてのビルダーに、親の `ceremony` と `protocol_modules`、ステージファイル、すべてのインラインコンテキスト、そして自身のエントリのパスだけを渡す。ステージのルールは `stage-protocol.md` の § "For subagent stages" のステップ 2 に従って渡す。ハーネスが独立したワーカーをサポートしている場合はエントリを並行してディスパッチする。エントリの逐次処理は汎用のフォールバックである。ビルダーが構築する各ユニットは、事前にチャットの中で専用のステップ（`directive.questions_only`、ステージファイルの QUESTION-ONLY モード）で質問済みである。そのため `build_required: true` のビルダーは、自身のエントリの `questions_file` からステージファイルの ARTIFACT-ONLY モードを実行し、利用者には何も質問せず、ユニットの成果物を書き込む。日誌は `directive.protocol_modules` に `learnings` が挙げられている場合にのみ付ける。エンジンがこのステージをウェーブとしてルーティングしている間は、最初の完了レシートの前も含め、逐次用の `unit start/pause/resume` 動詞は状態や監査を変更せずに拒否する。ウェーブディレクティブはバッチのチェックポイントであり、ブロッキングな質問がある場合は、`entry.required_produces` のパスを出さずにおくことでエントリを開いたままにし、質問をコンダクターに返して、人間の判断を待って停止する。

構築後、`review_state: "outstanding"` は指定されたイテレーションを実行する。`"retry-required"` は対応の取れていないリクエストを `aidlc-log.ts review --retry-pending` で繰り返す。`"repair-required"` はリードが単独で行う修復を実行し、その後に次のレビュアーイテレーションを実行する。`"recovery-required"` は出力された `review_iteration` で、古くなったレシートの回復を一度だけ実行する。`"escalation-required"` はその回復がすでに使われたことを意味する。別のレビューを要求したりユニットを完了したりしてはならない。停止して状況を人間に提示し、ステージの試行をリセットできるのは人間による Request Changes の判断だけである。`READY`、終端の `NOT-READY`、`not-required` にはレビュー作業は不要である。Guard Policy が `relaxed` または `off` の場合、レビュー後にユニットのレビュー済み成果物や申告済みソースが変更されても `"recovery-required"` にはならない。レシートは有効なまま残り、エンジンはゲートが開くかユニットが完了した時点でその変更を一度だけ記録し（`CHANGE_ACCEPTED`）、人間には `change_notices` の 1 行が伝えられる。単一のレビュアースコープ記録が強制される環境では、レビュアーのディスパッチは引き続き逐次化される。強制のないハーネスに限り、それらを並列のフォアグラウンド作業として実行してよい。エントリの構築が完了し、レビューが確定したら、`{{INVOKE}} engine state unit complete --wave --stage <slug> --unit <name>` を実行する。このコマンドはライブのウェーブエントリを再検証し、レシートを最終的な成果物のフィンガープリントに結び付け、その後に初めて `UNIT_COMPLETED` を出力する。したがって、その前にクラッシュした場合や、その後に成果物が変更された場合は `completion_required: true` が残り、エントリが再び引き渡される。Construction Checkpoints が有効な場合、完了済みエントリの出力への後からの変更は、代わりにユニットのチェックポイントが扱う。Guard Policy `strict` では一度だけ再チェックし、`relaxed` と `off` では一度だけそれを伝え、エントリは差し戻されない（ただし出力が消えている場合は差し戻される）。`relaxed` と `off` では、チェックポイントがなくても同じことが成り立つ。エントリは確定したまま残り、ステージのゲートがその変更を一度だけ伝える。依存するバッチもステージのゲートも、構築・レビュー・完了の証跡を追い越すことはできない。出力されたプレフィックスを処理した後は、report-approve を行わずに `next` を再実行する。unit-major の反復は逐次のままであり、決して `directive.wave` を伴わない。

学びのリチュアルが無効な場合、エンジンはユニットの日誌を作成しない。
