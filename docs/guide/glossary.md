# Glossary

AI-DLC 用語の正式な定義です。ユーザーガイドと開発者リファレンスのすべてのドキュメントは、これらの用語を一貫して使用しています。

---

| 用語 | 定義 |
|------|-----------|
| **Agent** | 同梱されている 14 のペルソナ（ドメインエキスパート 11、レビュー専用エージェント 2、adaptive-workflows のコンポーザー）のいずれかです。コンダクターは、それぞれの専門とするステージ、レビュー、または構成（composition）の役割に応じて各エージェントを起動します。 |
| **Approval gate** | 完了した作業（ステージ、検証済みのユニット、または完了したスウォームのバッチ）に対する決定です。人間の判断が必要なゲートは、あなたの実際の回答を待ちます。チェックポイントが有効なワークフローでは、記録された許可のもとで通常の完了を自動承認できますが、Plan Approval、有効化されたサマリー確認、検証コマンドの選択、スケルトンの承認は引き続き人間が決定します。サマリー確認は `directive.ceremony.summary_confirmation === "on"` の場合にのみ適用されます。Initialization や完了のみの記録処理では、人間への承認の質問は追加されません。 |
| **Autonomy mode** | `Construction Autonomy Mode` として保存される明示的な承認の設定で、`unset`、`gated`、`autonomous` のいずれかです。対象となるチェックポイントワークフローでは、“Continue automatically” を選ぶと `autonomous` が、“Review each checkpoint” を選ぶと `gated` が記録されます。これは実行順序やスウォームの選択とは独立に、通常の完了に関する質問を制御します。Plan Approval、有効化されたサマリー確認、検証コマンドの選択、スケルトンの承認、失敗時の対応は引き続き人間が必要です。既存のワークフローは従来のゲートポリシーを維持します。 |
| **Bolt** | 依存関係でつながった 1 つ以上のユニットにまたがる、計画された Construction の提供単位（デリバリースライス）です。ユニット、そのワークツリー、スウォームのバッチとは区別されます。Delivery Planning では、グルーピング、Definition of Done、確信度の仮説、オーナーシップを記録します。実行時の順序はユニットの DAG と記録されたイテレーションの選択に従い、`bolt-plan.md` がそれらを置き換えることはありません。Build and Test と CI Pipeline は、完了したユニットの作業全体に対して 1 回だけ実行されます。 |
| **Artifact** | ステージが生成し、インテントの記録ディレクトリ（`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`）に保存するファイルです。ほとんどは `requirements.md`、`code-summary.md`、`initiative-brief.md` のような Markdown ドキュメントで、`traceability.json` のように JSON のものも少数あります。 |
| **Audit trail** | インテントの記録ディレクトリ内の `audit/` にある追記専用のイベントログです。クローンごとのシャード（`<host>-<clone>.md`）として書き込まれ、読み取り側は glob で集めてタイムスタンプ順にマージします。134 種類のイベントを ISO タイムスタンプ付きで記録し、インテントから本番環境までの完全なトレーサビリティを提供します。 |
| **CLI tool** | この実装が実行する外部のコマンドラインユーティリティです。ネイティブインストールでは何も必要ありません（**Native channel** を参照）。コピーチャネルでは `bun` が必要です。Claude Code のツールと混同しないでください。 |
| **Claude Code tool** | Read、Write、Edit、Bash、Glob、Grep、Task、AskUserQuestion などの Claude Code 組み込みの機能です。エージェントはデフォルトでセッションのツールセット全体を継承します。任意の `tools:` 許可リストで絞り込むことができ、`disallowedTools: Task` が同梱されている唯一の制限です。 |
| **Codex** | OpenAI Codex CLI のハーネスで、現在の AI-DLC のハーネスディストリビューションの 1 つです。ソースビルドでは `core/` と `harness/codex/` から、git で無視されるローカルのプロジェクションを `dist/codex/` に生成します。リリースでは `runtime/codex/` 配下に含まれます。`$aidlc` で起動します。[Codex CLI 上の AI-DLC](harnesses/codex-cli.md) を参照してください。 |
| **Command** | AI-DLC をユーザーが呼び出す操作です。ハーネスのチャットコマンドでは、ワークフローに `/aidlc`（Codex では `$aidlc`）を使用します。ネイティブの `aidlc` コマンドは、プロジェクト、診断、プラグイン、マシンのライフサイクルに関するルートを提供します。 |
| **Compaction** | コンテキストウィンドウがいっぱいになったときに、それまでの会話コンテキストを要約する Claude Code の自動処理です。この実装では `aidlc-state.md` と監査証跡によって、コンパクションをまたいで状態を保持します。 |
| **Conductor** | `/aidlc` セッションそのもの（`SKILL.md`）で、薄い転送ループを実行します。**Engine** に次の手を問い合わせ、それを実行し（ステージの実行、あなたへの質問、スウォームの展開など）、結果を報告し、これを繰り返します。担うのは実行の品質であり、ルーティングではありません。[Engine とスキルシステム](../reference/17-skill-system.md) を参照してください。 |
| **Construction Verification Command** | ユニット／バッチのすべてのチェックポイントで再利用される、インテント単位のプロジェクトチェックです。ツールが管理する `VERIFICATION_COMMAND_RECORDED` レシートは、型付きの状態セッターが記録する前に、人間の **Approve**（エージェントが読み取った本人の返答で、その文言はそのまま保持されます。質問したチャット内、またはそれが最新の質問である間は新しいチャット内で行われたもの）を、正規化（トリム済み・1 行）したコマンドの SHA-256 に結び付けます。無関係な返答、**Request Changes**、別の質問への返答では、レシートは承認されません。状態フィールドだけでは実行は承認されません。Delivery Planning がコマンドを提案するか、グリーンフィールドで延期された場合は最初のチェックポイントで質問します（Kiro IDE と Kiro CLI v3 では、並列バッチの計画が承認された後、そのバッチの最初の `prepare` の前に質問します）。以降の変更には毎回新しい人間のレシートが必要です。証跡にはダイジェストと表示ラベルが保持され、コマンドの生テキストは保持されません。 |
| **Control loop** | ステージを方向付けて検証する、**Rules**（作業前に適用される恒常的な決定）と **Sensors**（出力に対して実行される決定的なチェック）によるフィードフォワード／フィードバックの組み合わせです。（CLI ディストリビューションの意味での **Harness** とは別物です。かつては両方とも "harness" と呼ばれていました。） |
| **Copy channel** | バージョン付きリリースの Bun 向け `aidlc-copy-runtime-X.Y.Z.tar.gz` から、完全な `runtime/<harness>/` ルートをコピーして行う手動のプロジェクトインストールです。Bun が必要で、ネイティブの `aidlc` 実行ファイルは不要です。 |
| **Core** | `core/` にある、人手で作成されたハーネス非依存の信頼できる唯一の情報源です。エンジン、ステージ、エージェント、ルール、スコープ、センサー、ナレッジ、フック、セッションスキルを含みます。すべてのハーネスディストリビューションはここから生成されます。編集はここで行い、決して `dist/` では行いません。 |
| **Cursor** | Cursor のハーネス（cursor.com）で、現在の AI-DLC のハーネスディストリビューションの 1 つです。ソースビルドでは `core/` と `harness/cursor/` から、git で無視されるローカルのプロジェクションを `dist/cursor/` に生成します。リリースでは `runtime/cursor/` 配下に含まれます。1 つのツリーで Cursor IDE と Cursor CLI（`agent`）の両方に対応します。14 のペルソナは `.cursor/agents/` のネイティブサブエージェントとして、オーケストレーター、ランナー、ユーティリティショートカットは `.cursor/skills/` のネイティブスキルとして提供されます。Cursor は `@` インポートを展開しないため、`.cursor/rules/aidlc.mdc` が恒常的なメソッドレイヤーを指し、4 つの `aidlc-phase-*.mdc` ルールがフェーズレイヤーを指します。`/aidlc` で起動し、`/aidlc-status`、`/aidlc-jump`、`/aidlc-scope` のショートカットがあります。[Cursor 上の AI-DLC](harnesses/cursor.md) を参照してください。 |
| **Depth** | 各ステージが生成する詳細さを制御する 3 段階の詳細レベル（Minimal、Standard、Comprehensive）のいずれかです。スコープにはデフォルトの深さがあり、任意の承認ゲートで上書きできます。[スコープ、深さ、テスト戦略](05-scopes-and-depth.md) を参照してください。 |
| **Directive** | **Engine** が各 `next` で出力する型付きの指示（例: `run-stage`、`ask`、`print`、`done`、`invoke-swarm`）で、**Conductor** に次に何をすべきかを正確に伝えます。[Engine とスキルシステム](../reference/17-skill-system.md) を参照してください。 |
| **Distribution** | **Packager** によって **Core** から生成される、1 つのハーネス向けのプロジェクションです。ソースビルドでは、git で無視されるローカルの `dist/claude/`、`dist/codex/`、`dist/copilot/`、`dist/cursor/`、`dist/kiro/`、`dist/kiro-ide/`、`dist/opencode/` ツリーと、それに対応するネイティブ用の `dist-release/<harness>/` を生成します。リリースでは、`dist/` のプロジェクションを手動コピー用に帯域外の `aidlc-copy-runtime-X.Y.Z.tar.gz` に、`dist-release/` のプロジェクションをネイティブインストール用にマニフェストに記載された `aidlc-runtime-X.Y.Z.tar.gz` に含めます。メンテナーが生成物を手で編集することは決してありません。 |
| **Engine** | 決定的なオーケストレーションツール（`aidlc-orchestrate.ts`。サブコマンドはちょうど 6 つ: `next`、`continue`、`report`、`park`、`team-board`、`wait`。`continue` は内部のステアリング用トランスポート、`team-board` は読み取り専用の Team Construction クエリ、`wait` はディスパッチされた作業を待つ時間制限付きの読み取り専用の待機です）です。ステージ間のルーティング（スコープの解決、ステージの順序付け、ジャンプ、再開、ゲートの状態）をすべて担い、**Conductor** が実行する型付きの **Directive** を出力します。[Engine とスキルシステム](../reference/17-skill-system.md) を参照してください。 |
| **External tool** | ステージが使用するサードパーティのツールやサービス（例: AWS CLI、Maven、npm）です。Claude Code のツールとは区別されます。 |
| **Fence** | 実行中のワークフローのどのステップも必要としないアクションを拒否するガードです。plan approval、review freeze、state transition、reviewer read scope、human presence の 5 つがあります。最初の 4 つは `/aidlc config set guard.<fence> off\|on` で 1 つの作業単位ごとに切り替えられます。`on` を指定すると、ポリシーによって下げられたフェンスを上げることができます。reviewer-scope のスイッチが影響するのはディスパッチされたレビュアーの読み取り／検索範囲であり、「チームで確保（claim）したチェックアウトは他のユニットの `construction/` サブツリーに書き込めない」という必須ルールには影響しません。利用者が入力した引き下げスイッチについては、エージェントが `--intent`/`--space` またはチャットで選択されたワークフローを使ってセッターを実行し、状態と監査行を書き込み、何が変わったかを伝えます。存在しない名前のインテントは拒否されます。状態ファイルがない場合、行に入力された設定（Guard Policy、plan approval、フェンスのスイッチ、その他のインテント設定）は、このチャットが次に開始する作業単位のために保持されます。利用者が自分の言葉で依頼した場合、またはガードの `lower-fence` の選択肢を選んだ場合は、エージェントが代わりにセッターを実行します。CLI のセッターは、直前の決定以降に利用者のターンが記録されていれば引き下げを行います。すでに off のフェンスや、ソースが `you` の同一ポリシー語であればキーは不要です。そのターンがない場合、利用者が自分のターミナルで入力したコマンドは本人の操作として引き下げを行います。それ以外では、`fenceKeyBypassed` のみが、フィクスチャ／ハーネス起動時のプレゼンスバイパスを通じて CLI での引き下げを許可します。メモリに保持された strict は最初に拒否を行い、それ以前の `Guards Off` エントリーを上書きします。無人実行ではプロンプト時の適用が抑止され、CLI での引き下げは拒否されます。フックは Windows でも動作するため、プロンプトを転送するすべてのハーネスで入力によるスイッチがサポートされます。モデルのツールはフックを呼び出したり、`aidlc/.aidlc-sessions/` や任意の `.aidlc-plan-approval/` ディレクトリに書き込んだりすることはできません。これは [state-transition ガード](../reference/06-hooks-and-tools.md#pretooluse-aidlc-state-transition-guardts) によって強制されます。Codex では `/aidlc` の代わりに `$aidlc` を使用します。human presence には作業単位ごとのスイッチはなく、`AIDLC_SKIP_HUMAN_PRESENCE_GUARD=1` によってのみ引き下げられます。フェンスが道を譲った場合、監査台帳が存在すれば `GUARD_STOOD_ASIDE` の監査行が記録されます。通知の配信方法はハーネスによって異なります。**Guard Policy** を参照してください。 |
| **Guard Policy** | インテントごとの設定（`strict`、`relaxed`、`off`）で、1 つの作業単位に対してガードがどこまで道を譲るか、つまり入力が変わったときに承認を再度開くかどうか、どのフェンスを維持するかを決めます。値はスコープのデフォルト（スコープファイルで宣言がなければ off）、次にインテント自身の状態行の順に解決され、`Mode: strict` を宣言したメモリレイヤーがあればその両方より優先されます。メモリレイヤーの `Mode: relaxed` や `Mode: off` は、スコープ由来の値を置き換えます。状態に `Guard Policy` と廃止された `Change Control` の両方が異なる語で記載されている場合、次の `next` が最後に設定されたと記録が示す方（なければ利用者自身のもの、スコープのもの、またはより厳しいもの）を唯一の行として残すまで、ソース `conflicting state lines` として strict が適用されます。両者が一致している場合は `Guard Policy` が使われ、次のポリシー書き込みで廃止された行が削除されます。`/aidlc --guard-policy relaxed\|off` や同じ内容の平易な依頼に対しては、エージェントがセッターを実行します。strict はコンダクターが直接設定できます。チャットからの明示的な `intent create --guard-policy relaxed\|off` は、スコープのデフォルトより低い場合は拒否されます。その場合は作業単位を作成し、利用者がより低い値を求めたときにエージェントがセッターを実行します。スコープのデフォルトは確認なしで適用されます。Compose による作成では、計画が実行される標準スコープ（一致した計画のスコープ、またはカスタム計画のベース）から Guard Policy を読み取り、スコープファイルは書き込みません。コンダクターは `strict` または `relaxed` の場合に `--guard-policy` を渡し（これにより低いスコープのデフォルトが引き上げられます）、`off` の場合は決して渡しません。一致した提案の Guard Policy を下げると、選択した値を持つ標準スコープ上のカスタム計画に変換され、上げた場合は一致した計画のままになります。いずれの場合も、インテントの作成時に適用され、後からセッターを実行する必要はありません。コンポーザーは進行中のインテントの値を変更せず、代わりにサポートされているポリシー変更の手段を案内します。以前は Change Control と呼ばれていました。古い表記も 1 リリースの間は読み取られます。**Fence** を参照してください。 |
| **Guardrail** | ルールファイル内の本文セクション（`## Forbidden`、`## Mandated`、およびフェーズルールのガードレール見出し）で、規範的な振る舞いの制約を表します。入れ物はルールであり、"guardrail" はその中の規範的な内容を指します。**Rule** を参照してください。 |
| **Harness** | AI-DLC コアの CLI ディストリビューションです。ハーネス非依存の **Core** を描画する先となる、高機能なコマンドラインエージェント 1 つを指します。対象は開かれており拡張可能です（現在: Claude Code、Kiro CLI、Kiro IDE、Codex CLI、Cursor、opencode、GitHub Copilot）。*注 — このリポジトリでは "harness" は文脈により 4 つの意味を持ちます:* (1) **この正式な CLI ディストリビューションの意味**、(2) ルールとセンサーによる **control loop**（旧用法で、現在は改名済み。**Control loop** を参照）、(3) `harness/<name>/` のソース側ディレクトリ、(4) `tests/harness/` のテストヘルパーディレクトリ。ユーザー向けドキュメントで「ハーネス」と言う場合は意味 1 のみです。 |
| **Hook** | イベントに応じて Claude Code が自動的に実行する TypeScript スクリプトです。この実装では 17 のフックを使用し、すべて `settings.json` でプロジェクト全体に登録されています。ワークフローの中核（監査ログ、センサーのディスパッチ、ランタイムグラフのコンパイル、ステータスラインの同期、トークン使用量の集約、コンパクション時の状態検証、サブエージェントの追跡、ターン終了時のループ強制）に加えて、セッションライフサイクル、人間のターンの発行、ディスパッチルールの正確な配信、state-transition・reviewer-scope・review-freeze・plan-approval の各ガード、そしてステータスラインコマンドがあります。ワークフロー固有の処理は自らゲートします。session-start はプロセスの親子関係を記録し、エージェントが実行するセッターは、入力された引き下げスイッチを選択中の作業単位に適用するか、チャットが次に開始する作業単位のために保持します。 |
| **Inline execution** | オーケストレーターがエージェントのペルソナを読み込み、会話の中で直接ステージを実行するデフォルトの実行モードです。リアルタイムのユーザーとのやり取りに対応します。 |
| **Intent** | スペースの `intents.json` レジストリの 1 行（`{uuid, slug, dirName, scope, repos, status}`）として追跡される作業単位で、`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` に独自の [Record dir] を持ちます。`<YYMMDD>` は記録が時系列順に並ぶようにするための UTC 日付のコンパクトな接頭辞（例: `260624` = 2026-06-24）で、`<label>` は依頼の要点を表す短いケバブケースの文字列です。同じ日に同じラベルが衝突した場合は数値のカウンター（`-2`、`-3`、...）で解決されます。正式で衝突しない ID は、ディレクトリの接尾辞ではなく、レジストリの行に保存された時系列順の UUIDv7 です。エンジンは最初の `/aidlc` で最初のインテントを自動作成します。明示的なセレクターまたはセッションごとのバインディングは、共有の `active-intent` カーソルより先にインテントを選択します。**Space**、**Record dir** を参照してください。 |
| **Kiro** | Kiro のハーネスで、現在の AI-DLC のハーネスディストリビューションの 1 つです。ソースビルドでは、git で無視されるローカルのプロジェクションを `dist/kiro/`（Kiro CLI (V2)。`aidlc config --harness kiro-v2` でセットアップ）と `dist/kiro-ide/`（Kiro。Kiro IDE と Kiro CLI v3 向けで、`aidlc config --harness kiro` でセットアップ）に生成します。リリースでは `runtime/` 配下に含まれます。AIDLC メソッドは、CLI エージェントのリソース、または IDE の常時読み込みステアリングのライブ参照を通じて、`aidlc/spaces/<active-space>/memory/` から読み込まれます。`/aidlc` で起動します。[Kiro での AI-DLC の実行](harnesses/kiro.md) と、その [Kiro CLI (V2)](harnesses/kiro.md#kiro-cli-v2) のセクションを参照してください。 |
| **Knowledge** | ステージ開始時にエージェントが読み込む参考資料です。2 つの階層があります。方法論のナレッジ（フレームワークとともに `.claude/knowledge/` で提供）と、チームのナレッジ（利用者が管理するスペース単位のドメインナレッジで、`aidlc/spaces/<space>/knowledge/` に置かれます。形式は自由で、ブートストラップ時は空であり、スペース内のすべてのインテントで共有されます）です。 |
| **Ladder prompt** | “Continue automatically” / “Review each checkpoint” の明示的な選択です。対象となるチェックポイントワークフローでは、選択が記録されていない場合に限り、スケルトンがオフなら Construction の開始時に、スケルトンがオンなら実際のスケルトンのチェックポイントの後に提示されます。オンデマンドでの許可／取り消しの依頼は引き続き利用できます。従来の最初のステージでのラダーは、統合されたスケルトンが構築済みであることを証明するものではありません。 |
| **Learning loop** | ステージ内での修正を、永続的なプラクティスやセンサーに変える仕組みです。学びがオンで、次回も通用するような形であなたがエージェントを修正した場合、エージェントはその後の人間の承認ゲートの前に、そうした修正ごとに 1 回、`You asked me to <your change>. Keep that for next time?` と質問し、**Yes, for this project**、**Yes, for the team**、**No** の選択肢を示します。修正がなければ何も質問しません。また、明示的に残すよう依頼したメモは、保持の質問なしで保持されます。保持された修正は、エージェントが選んだ見出しの下にプラクティスとして `aidlc/spaces/<active-space>/memory/project.md` または `team.md` に書き込まれ、現在のワークフローの次に該当するステージから適用されます。保持されたチェックは新しいセンサーの雛形を作成し、次のステージグラフのコンパイル時にバインドされます。ステージの `memory.md` 日誌が、保持の対象としてあなたに提示されることは決してありません。[ルールと学習ループ](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Lifecycle** | 方法論としての AI-DLC 全体、すなわち AI-Driven Development Life Cycle です。方法論の 1 回の実行がワークフローです。公開されているネイティブのコマンドは `config`、`doctor`、`version`、`update`、`use`、`uninstall` です。 |
| **Machine lifecycle command** | ユーザーごとのリリースや設定を管理するネイティブの `aidlc` ルートです。プロジェクトの `.aidlc-version` のピン留めには従わず、常にアクティブなバイナリから実行され、プロジェクトのワークフローデータは変更しません。 |
| **Manifest** | ハーネスの `harness/<name>/manifest.ts` で、**Packager** に対して **Core** をそのハーネスの **Distribution** にどう投影するか（ディレクトリのマッピング、ルールの名前変更、作成するファイル、任意の `emit` プラグイン）を伝える宣言的な契約です。ハーネスの追加は、ほぼマニフェストを 1 つ書くことで済みます。 |
| **MCP server** | プロジェクトルート（`.claude/` と同じ階層）の `.mcp.json` で宣言され、Claude Code セッションに提供される外部ツールサーバーです。この実装では 5 つを同梱しています: `context7` と 4 つの AWS サーバー（`aws-mcp`、`aws-pricing`、`aws-iac`、`aws-serverless`）です。すべてのエージェントはセッションのすべての MCP サーバーを継承し、エージェントごとの付与はありません。エージェントに特定のサーバーを*使わせない*ようにするには、その `tools:` 許可リストを特定の `mcp__<server>__<tool>` ID に絞り込みます。認証情報を持っていないサーバーは単に利用できないだけで、ワークフローを止めることは決してありません。[ハーネスのプリミティブ対応表 — MCP サーバー](../reference/14-claude-features.md#mcp-servers) と [はじめに](01-getting-started.md#mcp-servers-optional) を参照してください。 |
| **memory.md** | ステージごとの観察日誌で、（インテントの記録ディレクトリ配下の）`<record>/<phase>/<stage>/memory.md` に置かれます。ユニットごとに 1 回実行されるステージでは `<record>/construction/<unit>/<stage>/memory.md` に置かれます（配置を移したアップデートより前に開始された作業では、メモはステージの日誌に残り、引き続きそこから読み込まれます）。学びの儀式がオンの場合にのみ、エンジンが run-stage ディレクティブを出力する際に作成し、オーケストレーターが管理します（手で編集することは決してありません）。解釈（Interpretations）、逸脱（Deviations）、トレードオフ（Tradeoffs）、未解決の質問（Open questions）を記録します。これはエージェントの推論に関するステージの記録であり、学習ループが保持の対象としてあなたに提示することは決してありません。 |
| **Mob execution** | 時間制限のあるラウンドで行われる、ディスパッチされたメッシュ（`mode: mob`）です。リードが草案を作成し、互いの内容を見ない協力者が並行して貢献ファイルを書き、リードが統合します。解決できない判断は人間に回されることがあります。User Stories (2.4) が同梱されているモブです。協力者がオフの場合（`enterprise` 以外の同梱スコープすべて）、リードは単独で実行し、モブのラウンドは行われません。 |
| **Multi-repo intent** | 作業が複数の兄弟関係にあるコードリポジトリにまたがるインテントです。リポジトリの集合は作成時に、`--repos a,b` による明示指定、または兄弟リポジトリの自動検出（ワークスペースルート直下で `.git` を持つすべての子ディレクトリ。ただし、自前のコードを持つプロジェクトの git サブモジュールは除く）によって取得され、インテントの `intents.json` の行に `repos` として保存されます。Construction では、各 git 操作を `--repo <name>` で特定のリポジトリに結び付けます。リポジトリが記録されていないインテントは従来の単一リポジトリの場合で、git はプロジェクトディレクトリで実行されます。[成果物リファレンス](14-artifacts-reference.md) を参照してください。 |
| **Native channel** | 推奨されるユーザーごとのインストール方法です。ネイティブの `aidlc` バイナリと、バージョンが一致したハーネスランタイムを、マシンのバージョンディレクトリ配下に配置します。インストーラーとプロジェクトのブートストラップには Bun、Node.js、Git は不要です。Alpine の musl ホストでは、最初に `apk add libgcc libstdc++` で Bun と Node.js の共有ランタイムの前提パッケージをインストールします。 |
| **Offline package** | ネットワークにアクセスせずにインストールするために、そのまま転送されるリリースアセット一式です。プラットフォームごとのバイナリ、ランタイムペイロード、インストーラー、`version.json`、`checksums.txt`、`aidlc-release.intoto.jsonl` の来歴（provenance）バンドルを含みます。 |
| **opencode** | opencode のハーネス（opencode.ai）で、現在の AI-DLC のハーネスディストリビューションの 1 つです。ソースビルドでは `core/` と `harness/opencode/` から、git で無視されるローカルのプロジェクションを `dist/opencode/` に生成します。リリースでは `runtime/opencode/` 配下に含まれます。エンジンのツリーは `.aidlc/` に置かれます（opencode は `.opencode/tools/*.ts` をカスタムツールとして自動インポートするため、エンジンをそこに置くことはできません）。`.opencode/` にはネイティブのシェル（サブエージェント、`/aidlc` コマンド、フックアダプターのプラグイン）のみが含まれ、AIDLC メソッドはプロジェクトルートの `opencode.json` にある `instructions` の glob を通じて読み込まれます。`/aidlc` で起動します。[opencode 上の AI-DLC](harnesses/opencode.md) を参照してください。 |
| **GitHub Copilot** | GitHub Copilot のハーネスで、現在の AI-DLC のハーネスディストリビューションの 1 つです。ソースビルドでは `core/` と `harness/copilot/` から、git で無視されるローカルのプロジェクションを `dist/copilot/` に生成します。リリースでは `runtime/copilot/` 配下に含まれます。1 回のインストールで Copilot の両方の利用面（Copilot CLI と VS Code のエージェントモード。どちらも同じプロジェクトファイルを読み込みます）に対応します。エンジンのツリーは `.aidlc/` に置かれます。`.github/` には aidlc という名前のネイティブ出力（フックの接続設定 `hooks/aidlc.json`、ペルソナのカスタムエージェント、スキルのツリー）のみが含まれ、リポジトリの `.github/` を置き換えるのではなくマージされます。AIDLC メソッドはプロジェクトルートの `AGENTS.md` にある `@` インポート行を通じて読み込まれます。`/aidlc` で起動します。[GitHub Copilot 上の AI-DLC](harnesses/copilot.md) を参照してください。 |
| **Orchestrator** | ワークフローの駆動方法を表す総称で、次に何が起こるかを決める決定的な **Engine** と、それを実行する **Conductor**（`SKILL.md`）を指します。`/aidlc` で起動します。[Engine とスキルシステム](../reference/17-skill-system.md) を参照してください。 |
| **Packager** | `scripts/package.ts` で、**Core** と各 **Manifest** から、git で無視されるローカルの `dist/<harness>/`、`dist-release/<harness>/`、プラグインのプロジェクションをすべて生成するビルドです。`bun scripts/package.ts` ですべてをビルドします。`--check` は独立した一時ルートで 2 回ビルドし、結果をバイト単位で比較します。これが CI の決定性ガードです。 |
| **Parallel batch** | `unit-of-work-dependency.md` (2.7) に基づく、依存関係の準備が整ったユニットの実行時のグループで、互いに依存せず並行して実行できるものです。実行時のバッチは Bolt 計画のグルーピングではありません。自律的なスウォームでは、エンジンはすべての DAG バッチを収束させた後に、Code Generation のステージゲートを 1 つだけ提示します（中間のバッチごとにゲートを設けることはしません）。`SWARM_COMPLETED` が各実行時バッチを締めくくります。 |
| **Pipeline execution** | ディスパッチされたチェーン（`mode: pipeline`）で、各リンクは宣言された順序で実行され、それぞれが上流の作業をすべて参照できます。各リンクが戻るたびに、永続的な現在の試行のレシートが発行され、最後のリンクが成果物を完成させます。Reverse Engineering (2.1) が同梱されているパイプラインで、登録されたリポジトリごとに 1 つの完全なレシートチェーンが必要です。 |
| **Phase** | ライフサイクルの 5 つの主要な区分、Initialization (0)、Ideation (1)、Inception (2)、Construction (3)、Operation (4) のいずれかです。各フェーズには 3〜9 のステージが含まれます（Initialization 3、Ideation 7、Inception 9、Construction 7、Operation 7）。 |
| **Phase boundary verification** | Ideation、Inception、Construction の最後のステージ（Approval and Handoff、Delivery Planning、CI Pipeline）が `<record>/verification/` に書き込むトレーサビリティチェックで、下流のステージがそれを土台に作業する前に、リンクの欠落、孤立した成果物、不整合を検出します。これらのステージのいずれかをスキップする計画では、そのフェーズのチェックは行われません。[成果物リファレンス](14-artifacts-reference.md#phase-boundary-verification) を参照してください。 |
| **Plane** | ネットワークアーキテクチャから借用した、フレームワークが分離する 3 つの関心事のいずれかです。**control plane**（ステージの定義、ルール、センサー。何を実行すべきかのスキーマで、コンパイル時に解決されます）、**data plane**（実際のステージの実行、Bolt、監査テレメトリー）、**management plane**（`/aidlc --doctor`、監査クエリ、`CLAUDE.md`）があります。利用者向けの概要は [ルールと学習ループ](09-rules-and-the-learning-loop.md) を、完全なモデルは `docs/reference/02-plane-architecture.md` を参照してください。 |
| **Project pin** | コミットされた `.aidlc-version` の厳密な semver ファイルで、エンジンのコマンドに使う保持済みのネイティブエンジンを選択します。`aidlc config --pin` は完全なバイナリと一致するプロジェクトのハーネスを検証し、マシンローカルの解決済みターゲットを記録し、そのリリースが削除（prune）されないよう `pins.json` にピンを登録します。安定したコマンドランチャーは、整合性をチェックするアクティブなディスパッチャーを起動し、ディスパッチャーはプロジェクトの操作を実行する前に、ピン留めされたランタイムを検証して選択します。 |
| **Projection stamp** | 生成される `tools/data/aidlc-stamp.json` の識別情報で、投影されたツリーのフレームワークのバージョン、ディストリビューション、ハーネスディレクトリを記録します。起動時と doctor がバージョンのずれを検出するために使用します。 |
| **Record dir** | 1 つのインテントの成果物、ステージごとの `memory.md` 日誌、`aidlc-state.md`、`audit/` シャードを保持する、インテントごとのディレクトリです: `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`（`<record>/` と表記します）。インテントごとに専用のものがあります。明示的なセレクターまたはセッションごとのバインディングは、共有の `active-intent` ポインターより優先されます。**Space**、**Intent** を参照してください。 |
| **Refresh baseline** | Init が管理する `tools/data/aidlc-manifest.json` で、フレームワークが所有するファイルと型付きのルートへの寄与のハッシュを記録します。`aidlc config` はこれを使って、更新アクションの分類、ローカルの編集の検出、廃止された所有コンテンツの安全な削除、プロジェクトが所有するデータの保持を行います。 |
| **Release channel** | **Native channel** を参照してください。その `aidlc-runtime-X.Y.Z.tar.gz` ペイロードは、新たに再生成されたローカルの `dist-release/<harness>/` プロジェクションから組み立てられ、TLS と SHA-256 で認証され、リリースワークフローによって来歴が証明されます。 |
| **Retained version** | ユーザーごとのバージョンディレクトリ配下に並べて保存された、完全なネイティブバイナリ、リリースマニフェスト、0 個以上のハーネスランタイムです。アクティブなバージョン、ロールバック用のバージョン、登録済みのピン留めされたバージョンは削除（prune）から保護されます。 |
| **Root integration** | 宣言されたポリシー（管理ブロック、JSON マップ、JSON 配列、ファイル全体）のもとで `aidlc config` が調整する、プロジェクトルートのファイルへの寄与です。所有権は明示的であり、関係のないプロジェクトのコンテンツは保持されるか、競合として扱われます。 |
| **Reviewer** | 品質ゲートのエージェントで、`aidlc-product-lead-agent`（要件／ストーリー／モックアップ）または `aidlc-architecture-reviewer-agent`（技術設計）です。ステージが `reviewer:` と明示的に必須の Markdown の `review_artifact:` を宣言している場合に、ステージ本体が成果物を生成した後、別のサブエージェントとして呼び出されます。レビュアーはリクエストで指定されたレビューファイルに 1 つのレビュー（READY / NOT-READY と指摘事項）を書き込み、成果物には決して書き込みません。エンジンはそれをその成果物に紐付いたレビュー記録として記録します。リクエスト時の成果物／ソースのフィンガープリント、厳格な Verdict/Reviewer/Iteration フィールド、安定した完了スナップショットにより、変更された作業が認定されることを防ぎます。敵対的な NOT-READY の場合はビルダーが再実行し、`reviewer_max_iterations`（デフォルト 2）回までループした後、未解決の指摘事項を人間の承認ゲートで提示します。レビュアーは厳格なターン予算のもとで実行されます（Claude Code では `maxTurns: 60`、opencode では `steps: 60`、それ以外では文章による指定）。不完全なレビューは 1 回再試行し、それでも駄目なら最終的な NOT-READY として記録されます。レビュアーが進行を止めることは決してなく、常に人間が決定します。[エージェント](06-agents.md) を参照してください。 |
| **Rule** | ワークスペースルートのアクティブスペースのメモリレイヤー（`aidlc/spaces/<active-space>/memory/`）に一度だけ記述され、各ハーネスのネイティブなインクルード機構（Claude の `@` インポートスタブ、Kiro CLI のリソースまたは IDE のステアリング、Codex でのエンジンによるステップごとのルール配信、opencode の `instructions` glob、Copilot の `AGENTS.md` の `@` インポート）によってコンテキストに取り込まれ、対象となるすべてのステージに適用される、恒常的な振る舞いのルールです。ルールは厳密に加算的な 5 層のチェーン（org → team → project → phase → stage）を通じて解決され、該当するすべてのルールがコンテキストに現れます。より広いレイヤーが上書きされることは決してなく、追加されるだけです。ルールは **control loop** のフィードフォワード側を担い、決定的な検証のためにセンサーと組み合わせることができます。[ルールと学習ループ](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Runtime graph** | インテントの記録ディレクトリにある、ワークフローごとの `runtime-graph.json` 成果物です。構造的なステージグラフをデータプレーン側に写したもので、承認ゲートのたびに監査ログから生成されます。どのステージが実行されたか、どの Bolt が分岐したか、どのセンサーが実行されたか、`memory.md` のエントリー数を記録します。doctor と学習ループが読み取る、問い合わせ可能な実行ビューです。 |
| **Scope** | どのステージをどの深さで実行するかを決める 11 の名前付き構成（enterprise、feature、mvp、poc、bugfix、refactor、infra、security-patch、classic、workshop、express）のいずれかです。エージェントが自由形式のインテントから 1 つを提案し、あなたが確認します。 |
| **Sensor** | `.claude/sensors/` のマニフェストで定義される決定的な検証チェックです（例: `aidlc-linter.md`、`aidlc-type-check.md`）。センサーは、一致する Write/Edit の呼び出し時、または人間が回答する承認ゲートで既存の成果物ごとに 1 回（ステージ全体を読むチェックでは出力フォルダーごとに 1 回）実行され（Construction の自律モードで承認されるゲートでは、ブロッキングのセンサーのみが実行されます）、`SENSOR_*` の監査行を記録します。ゲートで実行されるバインディングは、助言的（advisory）またはブロッキング（blocking）のいずれかです。ブロッキングの指摘事項には、修正または明示的で監査される上書きが必要です。ステージは、どのセンサーを実行するかを `sensors:` frontmatter リストで宣言します。センサーは **control loop** のフィードバック側、ルールはフィードフォワード側を担います。[ルールと学習ループ](09-rules-and-the-learning-loop.md) を参照してください。 |
| **Test strategy** | 生成するテストの量と含めるテストの種類を制御する、3 段階のテスト量のレベル（Minimal、Standard、Comprehensive）のいずれかです。深さとは独立しており、スコープが上書きを宣言しない限り、アクティブな深さがデフォルトになります。[スコープ、深さ、テスト戦略](05-scopes-and-depth.md#the-3-test-strategy-levels) を参照してください。 |
| **Transaction** | 宛先のファイルシステム上にステージングされ、想定される現在の状態と照合された上で、アトミックなリネームによってコミットされる、プロジェクトまたはマシンへの変更です。コミットに失敗するとロールバックされます。復旧できない証跡は、doctor が報告する `.aidlc-recovery-*` の隔離領域に保持されます。 |
| **Session** | `/aidlc`（Codex では `$aidlc`）を実行する、ハーネス内での 1 つの会話（Claude Code のセッション、Kiro IDE のチャット、Codex CLI のセッションなど）です。ワークフローは再開の仕組みによって複数のセッションにまたがることがあります。 |
| **Skill** | ハーネスがコマンドとして提供する、YAML frontmatter 付きの Markdown ファイルです。Claude Code では `.claude/skills/` に置かれ `/` で入力し、Codex では `.agents/skills/` に置かれ `$` で入力します。ハーネスごとに専用のフォルダーがあります（[スキルとランナーコマンド](17-skills.md) を参照）。AI-DLC のオーケストレーターは `aidlc` スキルとして実装されています。ユーザー向けのドキュメントでは「スキル」より「コマンド」を優先して使います。 |
| **Space** | ワークスペース内の `aidlc/spaces/<space>/` にあるチームごとの領域で、独自の `memory/`、`knowledge/`、インテントの記録（`intents/`）を保持します。明示的なセレクターまたはセッションごとのバインディングは、git で無視される `aidlc/active-space` ポインター（デフォルトは `default`）より優先されます。単一チームの利用者には `spaces/default/` しか見えません。**Intent**、**Knowledge** を参照してください。 |
| **Stage** | ライフサイクルを構成する 33 の個別のステップのいずれかです。各ステージにはリードエージェントと定義済みの入出力があり、ステージプロトコルに従います。ステージはフェーズごとに番号が付けられています（例: 1.1、2.4、3.5）。 |
| **State file** | インテントごとの永続的なワークフローの状態で、（インテントの記録ディレクトリ配下の）`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/aidlc-state.md` にあります。6 状態のチェックボックス（`[ ]` / `[-]` / `[?]` / `[R]` / `[x]` / `[S]`）を使って、ステージの進捗、スコープ、ワークスペースのコンテキスト、セッション再開の情報を追跡します。 |
| **Subagent execution** | ディスパッチされたハブ（`mode: subagent`）で、コンダクターがハーネスのディスパッチツールを通じて別のエージェントコンテキストを呼び出します。Code Generation (3.5) は 1 つのエージェントに絞った実行です。Practices Discovery (2.2) はハブ＆スポーク型で、リードの草案、互いの内容を見ない 3 つの支援の貢献、人間へのインタビュー、そしてリードによる統合の順に進みます。協力者がオフの場合、リードはスポークなしで実行します。 |
| **Unit of work** | WHAT（何を作るか）にあたるもので、ソリューションのうち独立して実装可能な部分です。ステージ 2.7（Units Generation）で分解され、`unit-of-work-dependency.md` に一覧化されます。依存関係でつながった 1 つ以上のユニットが Bolt のスコープを構成します。 |
| **Walk order** | ソースコードを生成する新しい単独（solo）のユニットワークフローでは、デフォルトでユニット優先（unit-major）になります。つまり、1 つのユニットが該当するユニットごとのすべてのステージを通過してから、次のユニットに進みます。明示的なステージ優先（stage-major）も引き続き利用できます。対象となるスケルトンオンの作業では、どちらの順序でも、最初の統合ユニットを完了してから後続のユニットに進みます。従来のワークフロー、設計のみのワークフロー、チーム所有のワークフローは既存の進め方を維持します。実行時のバッチは `unit-of-work-dependency.md` から決まり、`bolt-plan.md` は計画上の内容です。 |
| **Walking skeleton** | 動作する最小の統合スライスで、スケルトンオンの場合に最初の DAG ユニットとして計画されます。対象となるチェックポイント有効の単独作業では、そのユニットが該当する設計ステージと Code Generation を完了し、記録された、人間が承認したエンドツーエンドの検証コマンドに合格し、人間の承認を受けてから、後続のユニットが開始されます。従来の最初の Construction ステージのレビューはステージゲートであり、動作するスケルトンの証拠ではありません。 |
| **Utility command** | `--status`、`--config`、`--doctor`、`--version`、`--stage`、`--phase`、`--scope` など、`/aidlc` に渡すターミナルフラグです。ワークフローのステージを実行することなく、特定の問い合わせ、設定の変更、移動の操作を行います。 |
| **Worktree** | スウォーム実行でユニットに使われる git の分離機構です。そのディレクトリと `bolt-<id8>_<slug>` ブランチがそのユニットの作業を保持し、ユニットの claim と同様にインテントのレジストリ UUID でスコープされます。[Bolt の識別子](../../core/knowledge/aidlc-shared/worktree-info-schema.md#bolt-identity) を参照してください。実行時には、ガイド付きまたは自動の完了承認を使用できます。ワークツリーは計画された Bolt でもスウォームのバッチでもありません。 |
| **Workspace** | `aidlc config` のインストール先となるフォルダー（実行したフォルダー、または `--project-dir` で指定したフォルダー）です。ハーネスのフォルダー、`aidlc/`、そして 1 つのコードリポジトリ（フォルダー自体がリポジトリ）または `aidlc/` と並ぶ複数のコードリポジトリを保持します。AI-DLC は git ルートを求めて上位ディレクトリを探索しないため、そのフォルダーがワークスペースになります。プロジェクトフォルダー、プロジェクトディレクトリ、ワークスペースルートとも呼ばれます。[`aidlc/` の置き場所](03-spaces-and-intents.md#where-aidlc-lives) を参照してください。 |
| **Workflow** | `/aidlc` の起動からステージの完了までの、AI-DLC ライフサイクルの 1 回のエンドツーエンドの実行です。特定のタスク（feature、bugfix など）を対象とします。 |
| **Workflow profile** | ユーザーガイドにおけるスコープの呼び名で、Classic、Express、Feature、Bugfix など、作業の種類ごとに厳選されたライフサイクルです。選択したプロファイルによって、ステージのルートと、`aidlc-state.md` に `Scope` として保存されるデフォルトが決まります。[ワークフロープロファイル](workflow-profiles.md) を参照してください。 |
