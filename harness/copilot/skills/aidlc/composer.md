# Composing a workflow plan (the adaptive composer)

エンジンの `print` がコンポーザーエージェントを指名したとき、つまり compose リクエスト、`--new-scope`、`--report <path>`、コールドスタート時の compose の提案に "compose" と回答された場合、またはワークフロー実行中の compose リクエストのときに、このファイルを読む。このファイルは同じディレクトリの `SKILL.md` を補完するものであり、そちらも引き続き適用される。

エンジンはスコープ確認の代わりに COMPOSER DISPATCH を指示することがある。`/aidlc compose "<task>"`、`--new-scope`、`--report <path>` のとき、または利用者がコールドスタート時の compose の提案に "compose" と回答したとき、`next` はコンポーザーエージェントを指名するメッセージを持つ `print` を出力する。これは他のディスパッチと同様に扱う。メッセージの指示をタスクとして、`aidlc-composer-agent` カスタムエージェントに委任する（エージェントは自身のペルソナを自分で読み込む）。コンポーザーは読み取り専用の `detect` スキャンを実行し、5 つのエントロピー要素（インテントの曖昧さ、構造的不確実性、検証エントロピー、リスク、未解決の前提）を見積もり、構造化された提案を返す: `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }`。すべての SKIP には理由が付き、さらに事前にレンダリングされた 2 つの Markdown 表（バンド付きの ARS スコア表と、理由付きのステージごとの判断表）が含まれる。

その提案を利用者に「短い」提案として提示し、続いて `question-rendering.md` に従って承認／編集／却下のゲートを提示する（Approve / Edit the plan / Reject。カスタムプランは承認がもう 1 つ増えるため、そのゲートは Approve / Approve and save as scope / Edit the plan / Reject となる）。**提案は短く保つ: 平易な推奨とプランを示し、詳細は求められたときに出す。** まず、自分の言葉で 2〜3 文: この変更がどのような種類のものに見えるか、したがってどの程度のプロセスを勧めるか、そしてステージ一覧を平易な言葉で（"a short run: design, build, test"）。次に、プランと、提案の `summary` にあるバリデーターの `shown` と `gates` の数値（Initialization 以降のステージ数で、進捗表示に使う数）を 1 行で示す。手で数え直してはならない。平易な言葉で "Plan: <scopeName>, <N> stages, <G> approval questions" と示す（カスタムプランの場合: "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` に `skipped_inputs`（このプランがスキップする各ステージと、それが作るものを使う残りのステージがあればそのステージ）が含まれる場合は、その後に平易な 1 行で、全件まとめて 1 回だけ、すべてを名指しして伝える: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution."。その後に下記の Guard Policy の行とスコープ設定の行を示し、各ステージを含める／除外する理由や規模判断の根拠となるスコアは求めれば見られる、と 1 行で伝える。返されたグリッドについては、コンポーザーの `mode` が最終決定である。コンポーザーはバリデーターの `nearest_stock` 距離に基づいて matched か custom かを振り分けており、matched の提案には再検証済みのストックグリッドがそのまま含まれている。グリッドを自分で比較して判定をやり直してはならず、どの提案もスコープファイルを書き込まない。`skipped_inputs` の行を除き、コンポーザーのステージ判断表（その下にある fold に関する注意事項を含む）と ARS スコア表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに示す: まずステージ表、次に **"Scoring detail (advisory)"** の下にスコア表を、その `method`（codekb | fallback）の行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。利用者が求めない限り、チャットでスコアの構成要素を説明しない。このゲートはステージゲートと同様にターンを必ず止めるものである: 沈黙を承認とみなしてはならず、明示的な承認の前にスコープデータを書き込んだりワークフローを作成したりしてはならない。編集の場合は、コンポーザーを再ディスパッチして変更を適用し、検証を再実行し、summary とステージ判断表を作り直して、短い提案を再提示する。編集で変更できるのは、ステージ、Guard Policy、スコープ設定である。編集が matched のストックグリッドを変更するか、その Guard Policy を下げる場合、承認に編集が反映されるよう、改訂後の提案は**必ず** CUSTOM にならなければならない。それ以外の設定変更は振り分けを維持し、`creationSettings` を通じてこの作業にのみ適用される。却下の場合は停止する（作業中であれば、ディスパッチの print が次に何をするかを示す）。利用者は代わりにスコープを直接指定できる。提案には `guardPolicy`（`strict`、`relaxed`、`off`）と 1 行の `guardPolicyRationale` も含まれる。これを提案の独立した行として示し（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"）、利用者が承認前に切り替えられるようにする。実行中は、その行を読み取り専用で示し（再構成で反映されるのはステージのスキップと追加だけである）、変更の経路を示す: 利用者がそれを上げる／下げるよう求めたら、利用者がそれを求めたメッセージを `<id>` として、`{{INVOKE}} engine config set guard-policy <value> --message <id>` を自分で実行する。利用者が同時に求めたスコープ変更よりも先に実行する。利用者が求めたスコープ変更には新しいスコープ自身のデフォルトが適用され、それ以外のスコープ変更は実行中のポリシーを維持し、そのことを 1 行で伝える。インテント作成時の Guard Policy は、プランが実行されるスコープから引き継がれる: matched プランならストックのデフォルト、カスタムプランならその `baseScope` のデフォルトであり、コンポーザーのバリデーターはその値以下のものを選んでいる。`strict` または `relaxed` の場合は `--guard-policy <value>` を渡し、`off` の場合は決して渡さない（作成時にはスコープ自身のデフォルトが記録されるか、それより低い値が引き上げられる）。このゲートで利用者が matched プランをストックのデフォルトより下に切り替えた場合、それは編集である: コンポーザーはその値を持つベースの上でカスタムプランに変換するため、後から設定コマンドを実行することはない。デフォルトより上への切り替えではプランは matched のままとなり、作成時にそのフラグで適用される。コンポーザーは実行中のインテントの Guard Policy を決して変更しない。提案には `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` はそれぞれ `on` または `off`、`review_cap` は `adversarial`、`advisory`、`none` のいずれか）と 1 行の `scopeSettingsRationale` も含まれる。これらは必ずもう 1 つの行として示し（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"）、利用者がそこで何を求めても、それを実現する。`scopeSettings` を持たない matched または custom の提案は、コンポーザーの振り分け後の検証を通過していない: コンポーザーが確認していない行を示すのではなく、コンポーザーを再ディスパッチする。このマシン上でキルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその同類）が `on` の値を強制的にオフにしているとコンポーザーが報告した場合は、その行の該当する値を、ここでは強制的にオフになっていると明示する。スコープファイルは書き込まれない: プランが実行されるストックスコープと異なる値は、`creationSettings` を通じてこの作業にのみ適用され、`--scope <scopeName>`（カスタムプランの場合: `--scope <baseScope>`）の後の作成フラグに変換される。変更は振り分けを維持するが、matched プランの Guard Policy を下げる変更だけは例外で、コンポーザーがカスタムプランに変換する。プランの承認では、提案に示された値が維持される: `creationSettings` 内の `plan_approval`（質問せずに構築するベースの上で、カスタムプランがそれを引き上げる場合）は、他の設定と同様に `--plan-approval` になり、それをオフにするのは利用者だけである。このゲートやスコープ確認の場で、利用者が自分の言葉でプランの承認をスキップするよう求めた場合は、ハーネスがそれを記録し、作成時にオフになる。したがって提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてのみ受け渡す: 各フラグは固定の名前から自分で組み立て（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）、値は許可された語のいずれかと完全に一致するものとする（`on` または `off`、`adversarial`、`advisory`、`none`）。キーや値がそれ以外であれば何も適用せずにコンポーザーを再ディスパッチし、コンポーザーのテキストを決してコマンドに貼り付けない。実行中の提案には設定の行はない。コンポーザーが `settingsChanges` として返す設定は、利用者が通常のチャットで求めた設定（`SKILL.md` を参照）とは異なる: これらはゲート上で "Also suggested by the composer" の下に示し、利用者が承認した場合にのみ適用する。こうして、利用者が求めていないものは何も変わらないようにする。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず、再構成も実行しない。`settingsChanges` のみの場合はそれをゲートで提示し（Approve / Reject）、承認されたらディスパッチの print の指示どおりに適用する。両方ある場合は Approve all / Approve stages only / Reject を提示する: Approve all では、ステージ変更と設定をそのフラグ（`--sensors off`、`--review none` など）として持つ再構成を 1 回だけ実行し、両方が同じ書き込みで反映されるようにする。ただし summary confirmation のオフは含めない（再構成はその引き下げを拒否するため）。その再構成が反映された後、利用者の承認メッセージを `<id>` として `{{INVOKE}} engine config set summary-confirmation off --message <id>` を自分で実行し、利用者の承認を実行に移す。Approve stages only では設定を含めずに再構成を実行する。

**構成時点の権限（Composition-moment authority）。** 上記の matched/custom のストック振り分けルールは、フロント／レポートの構成にのみ適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す: `nearest_stock` は参考情報にすぎず、現在のスコープ／深度と凍結済みのすべてのアクションは変更されず、ストックグリッドやスコープレジストリへの書き込みは許可されず、承認時には `changes.skip` / `changes.add` の配列をそのまま `recompose` に渡す。

**承認時（フロント／レポート）は、書き込みと作成を同じターンで実行する - 2 回目の `/aidlc` 呼び出しは不要:**

1. 先に書き込むものは何もない: プランはこの作業にのみ適用される。MATCHED プランはそのストックスコープ上で作成する。CUSTOM プランはその `baseScope` 上で、型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として渡して作成する（空でない各配列はカンマで連結し、空の配列は省略する。各要素は小文字・数字・ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずにコンポーザーを再ディスパッチする）。提案が `--depth <creationDepth>` を持つ場合はそれも渡し（値は厳密に `minimal`、`standard`、`comprehensive` のいずれか）、カスタムプランはさらに `--plan-name <scopeName>`、すなわち利用者がゲートで見た名前を渡す（小文字・数字・ハイフンからなる場合のみ。そうでなければ省略する）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで利用者に名前を尋ね、コンポーザーの `scopeName` を最初の選択肢として提示し、手順 3 の `next` コマンドに `--save-as <name>` を追加する: それが指示する作成処理がプランをそのスコープとして保存するので、その出力を伝える。名前は小文字の単語をハイフンで連結して自分で組み立て、作成処理がその名前は使用済みだと報告した場合は、別の名前を尋ねてその名前で再実行する。利用者がキーワードを付与した場合だけは例外である: `--save-as` は付けず、手順 3 の作成コマンドが成功した後、`next` を再実行する前に、`{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは小文字・数字・ハイフンからなる 1 語とする（それ以外のものは除外し、そのことを 1 行で伝える）。保存したスコープは、そうしなければ推定の対象にならない。
3. 承認された提案の、空白でない必須の `creationDescription` を使って、通常のインテント作成に進む。ディスパッチが `--request <id>` を渡している場合は、承認されたスコープでその `next --scope <name> --request <id>` コマンドを実行する（カスタムプランの場合は、`--scope <baseScope>` に続けてその `--skip` / `--add` と作成フラグを付ける）。リクエストのテキストを追記したり再構成したりしない。タスクに基づく `creationDescription` は、元のリクエストと一字一句同じでなければならない。ディスパッチがリクエスト本文を持つ代わりにリクエストの保存済みコピーを指定している場合、`creationDescription` は自分で書く短い要約である: 作成処理はそのコピーから元のテキストを読むので、リクエストを提案に決して貼り付けない。レポートのみ／タスクなしの提案では、承認前に根拠のある説明を作成し、ディスパッチの `--request` の id と、その説明を POSIX のシングルクォートで囲んだ 1 つの argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する。この id が作業をそのゲートに結び付け、一度だけ有効である。返された作成の print には、"Acting on a directive" の説明どおりに正確に従う。スコープのみの作成は決して実行しない。

**実行中の再構成（ワークフローが RUNNING の場合）:** 承認されたら、指示された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省略する。このコマンドは厳格に検証し（必須の入力が欠ける場合は拒否する）、カーソルより先にある PENDING のステージだけを切り替え、派生状態のフィールドを再構築し、RECOMPOSED を監査に記録する - 状態ファイルのサフィックスを手で編集してはならない。

コンポーザーが提案し、利用者が決定し、決定論的なバリデーターが守る。グリッドを散文で即興的に作ってはならず、コンポーザーがワークフローを前進させることも決してない。
