# Composing a workflow plan (the adaptive composer)

エンジンの `print` がコンポーザーエージェントを指名したときに、これを読む。対象は、compose リクエスト、`--new-scope`、`--report <path>`、コールドスタート時の compose の提案に "compose" と回答された場合、またはワークフロー実行中の compose リクエストである。これはこのファイルと同じ場所にある `SKILL.md` を補完するものであり、そちらも引き続き適用される。

エンジンは、スコープの確認の代わりに COMPOSER DISPATCH を指名することがある。`/aidlc compose "<task>"`、`--new-scope`、`--report <path>` の場合、または人間がコールドスタート時の compose の提案に "compose" と回答した場合、`next` はコンポーザーエージェントを指名するメッセージを含む `print` を出力する。他のディスパッチと同様にこれに従う。`task` ツールを使い、メッセージの指示をタスクとして `aidlc-composer-agent` に委譲する（エージェントは自身のペルソナを自分で読み込む）。コンポーザーは読み取り専用の `detect` スキャンを実行し、5 つのエントロピー要素（インテントの曖昧さ、構造的不確実性、検証エントロピー、リスク、未解決の前提）を見積もり、構造化された提案 `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }` を返す。提案には、すべての SKIP についての理由と、事前にレンダリングされた 2 つの Markdown 表（バンド付きの ARS スコア、および理由付きのステージごとの判定）が含まれる。

その提案を人間には「短い」提案として提示し、続いて `question-rendering.md` に従って承認/編集/却下のゲートを提示する（Approve / Edit the plan / Reject。カスタムプランでは 2 つ目の承認が加わるため、そのゲートは Approve / Approve and save as scope / Edit the plan / Reject となる）。**提案は短くまとめる。簡潔な推奨とプランを示し、詳細は求められたときに示す。** まず、自分の言葉で 2〜3 文で述べる。この変更がどのような種類のものに見えるか、したがってどの程度のプロセスを勧めるか、そしてステージの一覧を平易な言葉で（"a short run: design, build, test"（短い実行: 設計、構築、テスト））。次に 1 行で、プランと、提案の `summary` にあるバリデーターの `shown` と `gates` の数値（Initialization 以降のステージ数で、進捗行が使う数）を平易な言葉で示す。決して手作業で数え直さない: "Plan: <scopeName>, <N> stages, <G> approval questions"（カスタムプランの場合: "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` に `skipped_inputs`（このプランがスキップする各ステージと、その成果物を使う残存ステージがあればそれら）が含まれる場合は、その直後に平易な 1 行で、すべてをまとめて 1 回だけ、すべての名前を挙げて伝える: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution."。続いて、後述の Guard Policy の行とスコープ設定の行を示し、各ステージを含めた理由・除外した理由や、規模判定の根拠となるスコアを見たいときは尋ねられる旨を 1 行で伝える。コンポーザーの `mode` は、返されたグリッドに関して「最終的」である。コンポーザーはバリデーターの `nearest_stock` 距離に基づいて matched と custom を振り分けており、matched の提案にはすでに再検証済みのストックグリッドがそのまま含まれている。グリッドを自分で比較して判定を導き直してはならず、いかなる提案もスコープファイルを書き込まない。`skipped_inputs` の行を除き、コンポーザーのステージ判定表（その下にある fold に関する注意を含む）と ARS スコア表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに表示する。まずステージ表を示し、次に **"Scoring detail (advisory)"** の見出しの下にスコア表を、その `method` (codekb | fallback) の行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。ユーザーから求められない限り、チャットでスコアリングの要素を説明しない。このゲートはステージのゲートと同様に、ターンを必ず止めるハードストップである。沈黙を承認とみなしてはならず、明示的な承認の前にスコープデータを書き込んだりワークフローを作成したりしてはならない。編集の場合は、コンポーザーを再ディスパッチして変更を適用させ、検証を再実行し、サマリーとステージ判定表を作り直して、短い提案を再提示する。編集では、ステージ、Guard Policy、スコープ設定を変更できる。編集によって matched のストックグリッドが変わる場合、またはその Guard Policy が下がる場合、承認がその編集を反映するよう、改訂された提案は**必ず** CUSTOM にする。それ以外の設定変更はルートを維持し、`creationSettings` を通じてこの作業にのみ適用される。却下の場合は停止する（作業の実行中であれば、その後どうなるかはディスパッチの print が示す）。人間はスコープを直接指定することもできる。提案には `guardPolicy`（`strict`、`relaxed` または `off`）と 1 行の `guardPolicyRationale` も含まれる。人間が承認前に切り替えられるよう、これを提案の独立した行として表示する（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"（Guard Policy: relaxed - スパイクは速く進む。変更された入力は記録・通知されるが、再承認はされない））。実行中は、その行を読み取り専用で表示し（再構成で反映されるのはステージのスキップと追加のみ）、変更する経路を伝える。引き上げや引き下げを求められたら、`{{INVOKE}} engine config set guard-policy <value> --message <id>` を自分で実行する。`<id>` は利用者がそれを求めたメッセージであり、利用者が併せて求めたスコープ変更よりも先に実行する。利用者が求めたスコープ変更では新しいスコープ自体のデフォルトが適用され、それ以外のスコープ変更では実行中のポリシーが維持され、その旨を 1 行で伝える。インテントの作成では、プランが実行されるスコープの Guard Policy が引き継がれる。matched プランではストックのデフォルト、カスタムプランでは `baseScope` のデフォルトであり、後者はコンポーザーのバリデーターがその値以下になるよう選んだものである。`strict` または `relaxed` の場合は `--guard-policy <value>` を渡し、`off` の場合は決して渡さない（作成時にはスコープ自体のデフォルトが記録されるか、それより低い値は引き上げられる）。人間がこのゲートで matched プランをストックのデフォルトより下に切り替えた場合、それは編集である。コンポーザーはそれを、その値を持つベースの上のカスタムプランに変換するので、その後に設定コマンドは実行されない。デフォルトより上への切り替えではプランは matched のままとなり、作成時にそのフラグで適用される。提案には `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` はそれぞれ `on` または `off`、`review_cap` は `adversarial`、`advisory`、`none` のいずれか）と 1 行の `scopeSettingsRationale` も含まれる。これらは常にもう 1 行として表示し（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"（スコープ設定: センサー on、学び off、サマリー確認 off、プラン承認 on、コラボレーター off、レビューは advisory - 答えが明確な単発の修正））、人間がそこで求めたことは何であれ実行する。`scopeSettings` のない matched または custom の提案は、コンポーザーの振り分け済み検証を通過していない。コンポーザーが確認していない行を表示するのではなく、コンポーザーを再ディスパッチする。コンポーザーが、キルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその同類）によってこのマシンで `on` の値が強制的にオフになっていると報告した場合は、行内のその値に、ここでは強制的にオフであることを示す。スコープファイルは書き込まれない。プランが実行されるストックスコープと異なる値は、その `creationSettings` を通じてこの作業にのみ適用され、`--scope <scopeName>`（カスタムプランの場合は `--scope <baseScope>`）の後に続く作成フラグに変換される。変更はルートを維持するが、matched プランの Guard Policy を下げる場合だけは例外で、コンポーザーがそれをカスタムプランに変換する。プラン承認は提案が示す値を保持する。`creationSettings` 内の `plan_approval`（尋ねずにビルドするベースの上でそれを引き上げるカスタムプラン）は、他の設定と同様に `--plan-approval` になり、それをオフにできるのは利用者だけである。利用者がこのゲートまたはスコープの確認で、自分の言葉でプラン承認をスキップしたいと求めた場合は、ハーネスがそれを記録し、作成時にオフになる。したがって提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてのみ受け渡される。各フラグは固定の名前から自分で組み立てる（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）。値は許可された語のいずれかと完全に一致するものに限る（`on` または `off`、`adversarial`、`advisory`、`none`）。キーまたは値がそれ以外の場合は何も適用せず、コンポーザーを再ディスパッチする。コンポーザーのテキストを決してコマンドに貼り付けない。実行中の提案には設定の行はない。コンポーザーが `settingsChanges` として返す設定は、利用者が通常のチャットで求めた設定（`SKILL.md` を参照）とは異なる。それらはゲート上で "Also suggested by the composer" の下に示し、人間が承認したときにのみ適用する。こうすることで、利用者が求めていないものは何も変わらない。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず、再構成も実行しない。`settingsChanges` のみの場合は、それをゲート上で提示し（Approve / Reject）、承認されたらディスパッチの print の指示どおりに適用する。両方ある場合は Approve all / Approve stages only / Reject を提示する。Approve all の場合は、ステージの変更と設定をフラグ（`--sensors off`、`--review none` など）として含む再構成を 1 回だけ実行し、両方が同じ書き込みで反映されるようにする。ただしサマリー確認の off は除外する。再構成はその引き下げを拒否するためである。再構成が反映された後、`{{INVOKE}} engine config set summary-confirmation off --message <id>` を自分で実行する。`<id>` は利用者の承認であり、これによって利用者の承認が実行される。Approve stages only の場合は、設定を含めずに実行する。

**Composition-moment authority.**（コンポジション時点の権限）上記の matched/custom のストック振り分けルールは、フロント/レポートでのコンポジションに「のみ」適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す。`nearest_stock` は参考情報にすぎず、現在のスコープ/深さと凍結済みのすべてのアクションは変わらない。ストックグリッドやスコープレジストリへの書き込みは許可されず、承認時には正確な `changes.skip` / `changes.add` の配列を `recompose` に渡す。

**承認時（フロント/レポート）は、書き込みと作成を「同じ」ターンで行う - 2 回目の `/aidlc` 呼び出しは行わない:**

1. 最初に何かを書き込むことはない。プランはこの作業にのみ適用される。MATCHED プランはそのストックスコープ上で作成される。CUSTOM プランは、その型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として（空でない配列はそれぞれカンマで連結し、空の配列は省略する。各要素は小文字・数字・ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずにコンポーザーを再ディスパッチする）、その `baseScope` 上で作成される。提案に `--depth <creationDepth>` がある場合はそれも加え（値は厳密に `minimal`、`standard`、`comprehensive` のいずれか）、カスタムプランではさらに `--plan-name <scopeName>`（利用者がゲートで見た名前）を渡す（小文字・数字・ハイフンのみからなる場合に限る。それ以外の場合は省略する）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで人間に名前を尋ね、最初の選択肢としてコンポーザーの `scopeName` を提示する。そして手順 3 の `next` コマンドに `--save-as <name>` を追加する。それが指定する作成処理がプランをそのスコープとして保存するので、その出力を伝える。名前は、小文字の単語をハイフンでつないだ形で自分で組み立てる。名前がすでに使われていると作成処理が報告した場合は、別の名前を尋ね、その名前で再実行する。人間がキーワードを付与した場合だけは例外である。`--save-as` は付けず、手順 3 の作成コマンドが成功した後、`next` を再実行する前に、`{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは小文字・数字・ハイフンからなる 1 語とする（それ以外は除外し、その旨を 1 行で伝える）。保存されたスコープは、そうしない限り推論されない。
3. 承認された提案の、必須かつ空でない `creationDescription` を使って、通常のインテント作成に進む。ディスパッチが `--request <id>` を提供している場合は、承認されたスコープでその `next --scope <name> --request <id>` コマンドを実行する（カスタムプランの場合は、`--scope <baseScope>` の後にその `--skip` / `--add` と作成フラグを続ける）。リクエストのテキストを追加したり再構成したりしない。タスクに基づく `creationDescription` は、依然として元のリクエストと一字一句一致していなければならない。ディスパッチがリクエストを含めずに、その保存済みコピーを指定している場合、`creationDescription` は自分で書く短い要約とする。作成処理は元のテキストをそのコピーから読み込むので、リクエストを提案に貼り付けてはならない。レポートのみ/タスクなしの提案では、承認前に根拠のある説明を作成し、ディスパッチの `--request` id と、その説明を POSIX のシングルクォートで囲んだ 1 つの argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する。この id が作業をそのゲートに結び付け、1 回だけ有効である。返された作成の print には、"Acting on a directive" の説明どおりに正確に従う。スコープのみの作成は決して実行しない。

**実行中の再構成（ワークフローが RUNNING の場合）:** 承認されたら、指定された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省略する。このコマンドは厳密に検証し（必須入力が欠ける場合は拒否される）、カーソルより先にある PENDING のステージのみを切り替え、派生状態のフィールドを再構築し、RECOMPOSED を監査記録する。状態ファイルのサフィックスを決して手作業で編集しない。

コンポーザーが提案し、人間が決定し、決定的なバリデーターが守る。グリッドを散文の中で自分で即興で作ってはならず、コンポーザーはワークフローを前進させない。
