# Composing a workflow plan (the adaptive composer)

エンジンの `print` がコンポーザーエージェントを示したときにこれを読む: compose の依頼、`--new-scope`、`--report <path>`、"compose" と答えたコールドスタートの compose の申し出、またはワークフロー実行中の compose の依頼。これはこのファイルの隣にある `SKILL.md` を補うものであり、そちらも引き続き適用される。

エンジンは、スコープ確認の代わりに COMPOSER DISPATCH を示すことがある: `/aidlc compose "<task>"`、`--new-scope`、`--report <path>` のとき、または人間がコールドスタートの compose の申し出に "compose" と答えたとき、`next` はコンポーザーエージェントを示すメッセージを持つ `print` を出力する。他のディスパッチと同じように扱う: メッセージの指示をタスクとして、`task` ツールで `aidlc-composer-agent` に委任する（エージェントは自分のペルソナを自分で読み込む）。コンポーザーは読み取り専用の `detect` スキャンを実行し、5つのエントロピー要素（インテントの曖昧さ、構造的な不確実性、検証のエントロピー、リスク、未解決の前提）を見積もり、構造化された提案を返す: `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }`。すべての SKIP に理由が付き、さらに事前に描画された Markdown の表が2つ付く（帯付きの ARS スコア、理由付きのステージごとの判断）。

その提案を人間に「短い」申し出として示し、その後 `question-rendering.md` に従って承認/編集/却下のゲートを提示する（Approve / Edit the plan / Reject。カスタム計画では2つ目の承認が加わるので、ゲートは Approve / Approve and save as scope / Edit the plan / Reject になる）。**申し出は短く保つ: 平易な推奨と計画を示し、詳細は求められたら示す。** まず、自分の言葉で2〜3文: この変更がどのような種類のものに見えるか、したがってどの程度のプロセスを勧めるか、そしてステージの一覧を平易な言葉で（"a short run: design, build, test"）。次に、計画と、提案の `summary` にある検証器の `shown` と `gates` の数（Initialization の後のステージ数で、進捗行が使う数）を1行で、手で数え直さずに、平易な言葉で示す: "Plan: <scopeName>, <N> stages, <G> approval questions"（カスタム計画の場合: "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` が `skipped_inputs`（この計画がスキップする各ステージと、あれば、計画に残るステージのうちその生成物を使うもの）を持つ場合は、その後に平易な1行で、すべてをまとめて1回だけ、1つ残らず名前を挙げて伝える: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution." その次に、後述の Guard Policy とスコープ設定の行を示し、各ステージが含まれる/除外される理由と、規模の判断の根拠となるスコアを見せるよう頼めることを1行で伝える。コンポーザーの `mode` は返されたグリッドについて最終的なものである: コンポーザーは検証器の `nearest_stock` の距離に基づいて matched と custom を振り分けており、matched の提案は再検証された標準のグリッドをすでにそのまま持っている - グリッドを自分で比較して判定を導き直してはならず、どの提案もスコープファイルを書かない。`skipped_inputs` の行を除き、コンポーザーのステージ判断の表（その下にある統合の助言を含む）と ARS スコアの表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに示す: まずステージの表、次に **"Scoring detail (advisory)"** の下にスコアの表を、その `method`（codekb | fallback）の行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。ユーザーが求めない限り、スコアリングの要素をチャットで説明しない。このゲートは、ステージゲートと同様に厳格なターンの停止点である: 沈黙を承認とみなしてはならず、明示的な承認の前にスコープのデータを書いたりワークフローを作成したりしてはならない。編集の場合は、変更を適用するためにコンポーザーを再ディスパッチし、検証を再実行し、サマリーとステージ判断の表を作り直し、短い申し出を再提示する。編集で変えられるのは、ステージ、Guard Policy、スコープ設定である。編集が matched の標準グリッドを変えるか、その Guard Policy を下げる場合、修正後の提案は**必ず** CUSTOM にし、承認が編集を運ぶようにする。それ以外の設定変更はルートを保ち、`creationSettings` を通じてこの作業に適用される。却下の場合は停止する（作業の実行中は、ディスパッチの print が次に何が起きるかを伝える）。人間は代わりにスコープを直接指定できる。提案は `guardPolicy`（`strict`、`relaxed`、`off`）と1行の `guardPolicyRationale` も持つ: それを提案の独立した行として表示し（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"）、人間が承認前に切り替えられるようにする。実行中は、その行を読み取り専用で表示し（再構成で反映されるのはステージのスキップと追加だけである）、方法を示す: 上げたい、または下げたいと求められたら、利用者が一緒に求めたスコープ変更よりも前に、`{{INVOKE}} engine config set guard-policy <value> --message <id>` を `<id>` を利用者が依頼したメッセージとして自分で実行する。利用者が求めたスコープ変更は新しいスコープ自身のデフォルトを伴い、それ以外のスコープ変更は実行中のポリシーを保ち、そのことを1行で伝える。インテントの作成は、計画が実行されるスコープから Guard Policy を引き継ぐ: matched の計画なら標準のデフォルト、カスタム計画なら `baseScope` のデフォルトであり、コンポーザーの検証器はその値以下のものを選んでいる。`strict` または `relaxed` の場合は `--guard-policy <value>` を渡し、`off` の場合は決して渡さない（作成時にはスコープ自身のデフォルトが記録されるか、それより低い値が引き上げられる）。このゲートで人間が matched の計画を標準のデフォルトより下に切り替えた場合、それは編集である: コンポーザーはその値を持つベースの上のカスタム計画に変換するので、後から設定コマンドは実行されない。デフォルトより上への切り替えでは計画は matched のままで、作成時にそのフラグで適用される。コンポーザーが実行中のインテントの Guard Policy を変えることはない。提案は `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` がそれぞれ `on` または `off`、`review_cap` が `adversarial`、`advisory`、`none` のいずれか）と1行の `scopeSettingsRationale` も持つ: 常にそれらをもう1つの行として表示し（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"）、人間がそこで求めたことは何であれ実行する。`scopeSettings` のない matched またはカスタムの提案は、コンポーザーのルーティングされた検証を通過していない: コンポーザーが確認していない行を表示せず、コンポーザーを再ディスパッチする。コンポーザーが、キルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその同類）によってこのマシンで `on` の値が強制的にオフになっていると報告した場合は、行のその値をここでは強制オフと示す。スコープファイルは書かれない: 計画が実行される標準スコープと異なる値は、その `creationSettings` を通じてこの作業にだけ適用され、`--scope <scopeName>`（カスタム計画の場合は `--scope <baseScope>`）の後の作成フラグに変換される。変更はルートを保つが、matched の計画の Guard Policy を下げる場合は例外で、コンポーザーがそれをカスタム計画に変える。計画承認は提案が示す値を保つ: `creationSettings` 内の `plan_approval`（尋ねずにビルドするベースの上でカスタム計画がそれを引き上げる場合）は、他の設定と同様に `--plan-approval` になり、それをオフにするのは利用者だけである。このゲートやスコープ確認の場面で、利用者が自分の言葉で計画承認のスキップを求めた場合は、ハーネスがそれを記録し、作成時にオフになるので、提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてだけ運ばれる: 各フラグは固定の名前から自分で組み立て（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）、値は許可された語のいずれかに厳密に一致するものとする（`on` または `off`、`adversarial`、`advisory`、`none`）。キーや値がそれ以外の場合は何も適用せずにコンポーザーを再ディスパッチし、コンポーザーのテキストをコマンドに貼り付けてはならない。実行中の提案は設定の行を持たない。コンポーザーが `settingsChanges` として返す設定は、利用者が普通のチャットで求める設定とは異なる（`SKILL.md` を参照）: ゲート上で "Also suggested by the composer" の下に示し、人間が承認したときにだけ適用する。そうすれば、利用者が求めていないものは何も変わらない。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず、再構成も実行しない。`settingsChanges` だけがある場合は、それをゲートで提示し（Approve / Reject）、承認されたらディスパッチの print の指示どおりに適用する。両方がある場合は Approve all / Approve stages only / Reject を提示する: Approve all では、ステージの変更と設定をフラグ（`--sensors off`、`--review none` など）として持つ再構成を「1回だけ」実行し、両方が同じ書き込みで反映されるようにする。ただし、再構成はサマリー確認をオフにする引き下げを拒否するので、それは含めず、反映された後に `{{INVOKE}} engine config set summary-confirmation off --message <id>` を `<id>` を利用者の承認として自分で実行し、利用者の承認を実行に移す。Approve stages only では、設定なしで実行する。

**構成時点での権限。** 上記の matched/custom の標準ルーティングのルールは、front/report の構成に「だけ」適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す: `nearest_stock` は助言的なものであり、現在のスコープ/深さと凍結されたすべてのアクションは変わらず、標準グリッドやスコープレジストリへの書き込みは許されず、承認は正確な `changes.skip` / `changes.add` の配列を `recompose` に渡す。

**承認時（front/report）は、書き込みと作成を「同じ」ターンで実行する - `/aidlc` の2回目の呼び出しは行わない:**

1. 先に何かを書き込むことはない: 計画はこの作業にだけ適用される。MATCHED の計画はその標準スコープ上に作成される。CUSTOM の計画はその `baseScope` 上に、型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として作成される（空でない各配列はカンマで連結し、空のものは省く。各エントリは小文字の英字、数字、ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずにコンポーザーを再ディスパッチする）。提案が `--depth <creationDepth>` を持つ場合はそれも加え（厳密に `minimal`、`standard`、`comprehensive` のいずれか）、カスタム計画では `--plan-name <scopeName>`、つまり利用者がゲートで見た名前も渡す（小文字の英字、数字、ハイフンからなる場合のみ。そうでなければ省く）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで人間に名前を尋ね、コンポーザーの `scopeName` を最初の選択肢として示し、手順 3 の `next` コマンドに `--save-as <name>` を加える: それが示す作成によって計画がそのスコープとして保存されるので、その出力を伝える。名前は小文字の語をハイフンでつないだ形で自分で組み立て、作成時にその名前が使用済みと報告されたら別の名前を尋ねて、それで再実行する。人間がキーワードを与えた場合は唯一の例外である: `--save-as` を付けず、手順 3 の作成コマンドが成功した後、`next` を再実行する前に、`{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは小文字の英字、数字、ハイフンからなる1語とする（それ以外は除外し、そのことを1行で伝える）。そうしなければ、保存されたスコープは推論の対象に「ならない」。
3. 承認された提案の、必須で空でない `creationDescription` を使って、通常のインテント作成に進む。ディスパッチが `--request <id>` を提供する場合は、承認されたスコープでその `next --scope <name> --request <id>` コマンドを実行する（カスタム計画では `--scope <baseScope>` の後にその `--skip` / `--add` と作成フラグを続ける）。リクエストのテキストを付け足したり組み立て直したりしない。タスクに基づく `creationDescription` は、元のリクエストと逐語的に一致していなければならない。ディスパッチがリクエストを運ぶ代わりにその保存されたコピーを示している場合、`creationDescription` は自分で書く短い要約である: 作成時に元のテキストはそのコピーから読まれるので、リクエストを提案に貼り付けてはならない。レポートのみ/タスクなしの提案では、承認前に根拠のある説明を導き出し、ディスパッチの `--request` の id とその説明を1つの POSIX シングルクォートの argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する。id は作業をそのゲートに結び付け、1回だけ使える。返された作成の print には "Acting on a directive" の説明どおりに正確に従う。スコープのみの作成を実行してはならない。

**実行中の再構成（ワークフローが実行中）:** 承認されたら、示された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省く。これは厳密に検証し（必須の入力が不足すると拒否される）、カーソルより先の PENDING のステージだけを切り替え、導出された状態フィールドを作り直し、RECOMPOSED を監査ログに記録する - 状態ファイルのサフィックスを手で編集してはならない。

コンポーザーが提案し、人間が決定し、決定論的な検証器が守る。あなたが散文で自分でグリッドを即興することはなく、コンポーザーがワークフローを進めることもない。
