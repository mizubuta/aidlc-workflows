# Composing a workflow plan (the adaptive composer)

エンジンの `print` がコンポーザーエージェントを指定したときにこのファイルを読む。対象は、compose 要求、`--new-scope`、`--report <path>`、コールドスタート時の compose 提案に "compose" と回答された場合、またはワークフロー実行中の compose 要求である。このファイルは同じ場所にある `SKILL.md` を補完するものであり、そちらも引き続き適用される。

エンジンは scope の確認の代わりに COMPOSER DISPATCH を指定することがある。`/aidlc compose "<task>"`、`--new-scope`、`--report <path>` のとき、または人間がコールドスタート時の compose 提案に "compose" と回答したとき、`next` はコンポーザーエージェントを指定するメッセージを持つ `print` を出力する。これは通常のディスパッチと同様に扱う。ディスパッチツールで `aidlc-composer-agent` に委譲し、メッセージの指示をタスクとして渡す（エージェント設定が自身のペルソナを読み込む）。コンポーザーは読み取り専用の `detect` スキャンを実行し、5つのエントロピー要素（インテントの曖昧さ、構造的不確実性、検証エントロピー、リスク、未解決の前提）を見積もり、構造化された提案 `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }` を返す。提案にはすべての SKIP の理由と、事前レンダリングされた2つの Markdown 表（バンド付きの ARS スコア表、理由付きのステージごとの判定表）が含まれる。

その提案を人間に「短い提案」として提示し、続いて `question-rendering.md` に従って承認/編集/却下のゲートを提示する（Approve / Edit the plan / Reject。カスタムプランでは2つ目の承認が加わり、ゲートは Approve / Approve and save as scope / Edit the plan / Reject となる）。**提案は短く保つ。平易な推奨とプランだけを示し、詳細は求められたときに出す。** まず、自分の言葉で2〜3文で述べる。この変更がどのような種類のものに見えるか、したがってどの程度のプロセスを勧めるか、そしてステージの一覧を平易な言葉で（"a short run: design, build, test"）。次に、プランと、提案の `summary` にある検証器の `shown` と `gates` の数（Initialization 以降のステージ数で、進捗行が使う数）を1行で示す。決して手で数え直さず、平易な言葉で "Plan: <scopeName>, <N> stages, <G> approval questions" とする（カスタムプランの場合は "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` に `skipped_inputs`（このプランがスキップする各ステージと、そのステージが作るものを使う、プランに残るステージがあればそれら）が含まれる場合は、その直後に平易な1行で、すべてをまとめて1回だけ、漏れなく名前を挙げて述べる: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution." その後に、下記の Guard Policy の行と scope 設定の行を示し、各ステージを含める/外す理由と、規模判断の根拠となるスコアを見たいと依頼できることを1行で伝える。コンポーザーの `mode` は返されたグリッドについて最終決定である。コンポーザーは検証器の `nearest_stock` 距離に基づいて matched と custom を振り分けており、matched の提案には再検証済みの標準グリッドがそのまま含まれている。グリッドを自分で比較して判定を導き直してはならず、どの提案も scope ファイルを書き込まない。`skipped_inputs` の行を除き、コンポーザーのステージ判定表（その下の fold に関する注意書きを含む）と ARS スコア表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに示す。まずステージ表、次に **"Scoring detail (advisory)"** の下にスコア表を、その `method`（codekb | fallback）行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。ユーザーに求められない限り、スコアの構成要素をチャットで説明しない。このゲートはステージのゲートと同様に厳格なターン停止である。沈黙を承認として扱ってはならず、明示的な承認の前に scope データを書き込んだりワークフローを作成したりしてはならない。編集の場合は、コンポーザーを再ディスパッチして変更を適用させ、検証を再実行し、サマリーとステージ判定表を作り直し、短い提案を再提示する。編集で変更できるのは、ステージ、Guard Policy、scope 設定である。編集が matched の標準グリッドを変更する場合、またはその Guard Policy を引き下げる場合、承認に編集内容が反映されるよう、修正後の提案は 必ず CUSTOM にしなければならない。それ以外の設定変更はルートを維持し、`creationSettings` を通じてこの作業にのみ適用される。却下の場合は停止する（作業が実行中なら、その後どうなるかはディスパッチの print が示す）。人間は代わりに scope を直接指定できる。このハーネスでは、あなたもコンポーザーも scope ファイルを書き込まない。scope の保存はエンジンの `scope save` が行う（下記の手順 2）。提案には `guardPolicy`（`strict`、`relaxed`、`off` のいずれか）と1行の `guardPolicyRationale` も含まれる。これを提案の独立した行としてレンダリングし（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"）、人間が承認前に切り替えられるようにする。実行中の場合はその行を読み取り専用でレンダリングし（再構成で反映されるのはステージのスキップと追加のみ）、経路を示す。利用者が引き上げや引き下げを求めたら、依頼された他の scope 変更よりも前に、`<id>` を依頼のあったメッセージとして `{{INVOKE}} engine config set guard-policy <value> --message <id>` を自分で実行する。利用者が求めた scope 変更には新しい scope 自身の既定値が適用され、それ以外の scope 変更では実行中のポリシーが維持され、その旨を1行で伝える。インテント作成時の Guard Policy は、プランが実行される scope から引き継がれる。matched プランなら標準の既定値、カスタムプランなら `baseScope` の既定値であり、コンポーザーの検証器はその値以下の base を選んでいる。`strict` または `relaxed` の場合は `--guard-policy <value>` を渡し、`off` の場合は決して渡さない（作成時には scope 自身の既定値が記録されるか、より低い値が引き上げられる）。このゲートで人間が matched プランをその標準の既定値より下に切り替えた場合、それは編集である。コンポーザーがその値を持つ base 上のカスタムプランに変換するため、後から設定コマンドを実行することはない。既定値より上への切り替えではプランは matched のままで、作成時にそのフラグで適用される。提案には `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` はそれぞれ `on` または `off`、`review_cap` は `adversarial`、`advisory`、`none` のいずれか）と1行の `scopeSettingsRationale` も含まれる。これらは常にもう1行としてレンダリングし（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"）、人間がそこで何を求めても、それを実行する。`scopeSettings` を持たない matched またはカスタムの提案は、コンポーザーの経路付き検証を通過していない。検証されていない行をレンダリングせず、コンポーザーを再ディスパッチする。コンポーザーが、キルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその同類）によってこのマシンで `on` の値が強制的にオフになっていると報告した場合、行の中でその値をこの環境で強制オフ（forced off here）と表示する。scope ファイルは書き込まれない。プランが実行される標準 scope と異なる値は、`creationSettings` を通じてこの作業にのみ適用され、`--scope <scopeName>`（カスタムプランなら `--scope <baseScope>`）の後に続く作成フラグに変換される。変更はルートを維持する。ただし matched プランの Guard Policy を引き下げる変更は例外で、コンポーザーがカスタムプランに変換する。プラン承認は提案が示す値を維持する。`creationSettings` 内の `plan_approval`（質問せずに構築する base の上でカスタムプランがそれを引き上げる場合）は、他の設定と同様に `--plan-approval` になり、それをオフにできるのは利用者だけである。このゲートまたは scope 確認で、利用者が自分の言葉でプラン承認を省くよう求めた場合、ハーネスがそれを記録し、作成時にオフになる。したがって提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてのみ受け渡す。各フラグは固定名から自分で組み立て（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）、値は許可された単語（`on` または `off`、`adversarial`、`advisory`、`none`）のいずれかと完全に一致するものとする。キーや値がそれ以外のものであれば、何も適用せずコンポーザーを再ディスパッチし、コンポーザーのテキストを決してコマンドに貼り付けない。実行中の提案には設定行はない。コンポーザーが `settingsChanges` として返す設定は、利用者が通常のチャットで求める設定（`SKILL.md` を参照）とは異なる。それらはゲート上の "Also suggested by the composer" の下に示し、人間が承認した場合にのみ適用する。こうして、利用者が求めていないものは何も変わらない。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず再構成も実行しない。`settingsChanges` だけがある場合は、それをゲート（Approve / Reject）で提示し、承認されたらディスパッチの print の指示どおりに適用する。両方がある場合は Approve all / Approve stages only / Reject を提示する。Approve all では、ステージ変更と設定をフラグ（`--sensors off`、`--review none` など）として持つ再構成を1回だけ実行し、両方が同じ書き込みで反映されるようにする。ただしサマリー確認の off は含めない。再構成はその引き下げを拒否するためである。再構成が反映された後、`<id>` をその承認として `{{INVOKE}} engine config set summary-confirmation off --message <id>` を自分で実行し、承認内容を実行する。Approve stages only では設定を含めずに再構成を実行する。

**Composition-moment authority（構成時点での権限）。** 上記の matched/custom の標準ルーティング規則は、フロント/レポートでの構成にのみ適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す。`nearest_stock` は参考情報であり、現在の scope/深さと凍結されたすべてのアクションは変更されない。標準グリッドや scope レジストリへの書き込みは許可されず、承認時には `changes.skip` / `changes.add` の配列をそのまま `recompose` に渡す。

**承認時（フロント/レポート）、書き込みと作成は同じターンで行う。2回目の `/aidlc` 呼び出しは行わない:**

1. 最初に書き込むものは何もない。プランはこの作業にのみ適用される。MATCHED プランはその標準 scope 上で作成される。CUSTOM プランはその `baseScope` 上で、型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として作成される（空でない配列はそれぞれカンマで連結し、空の配列は省く。各要素は英小文字・数字・ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずコンポーザーを再ディスパッチする）。提案に `--depth <creationDepth>` がある場合はそれを加え（値は正確に `minimal`、`standard`、`comprehensive` のいずれか）、カスタムプランでは `--plan-name <scopeName>`、つまり利用者がゲートで見た名前も渡す（英小文字・数字・ハイフンのみからなる場合に限る。そうでなければ省く）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで人間に名前を尋ね、最初の選択肢としてコンポーザーの `scopeName` を提示し、手順 3 の `next` コマンドに `--save-as <name>` を加える。それが指定する作成処理がプランをその scope として保存するので、その出力を伝える。名前は英小文字の単語をハイフンでつないだ形で自分で組み立て、作成処理がその名前は使用済みだと報告したら、別の名前を尋ねてその名前で再実行する。人間がキーワードを与えた場合は唯一の例外である。`--save-as` は付けず、手順 3 の作成コマンドが成功した後、`next` を再実行する前に `{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは英小文字・数字・ハイフンからなる1語とする（それ以外は除外し、その旨を1行で伝える）。保存された scope は、そうしなければ推論の対象にならない。
3. 承認された提案の、必須で空でない `creationDescription` を用いて通常のインテント作成に進む。ディスパッチが `--request <id>` を提供している場合は、承認された scope で `next --scope <name> --request <id>` コマンドを実行する（カスタムプランの場合は `--scope <baseScope>` の後にその `--skip` / `--add` と作成フラグを続ける）。依頼テキストを追記したり再構成したりしない。タスクに基づく `creationDescription` は、元の依頼と一字一句同じでなければならない。ディスパッチが依頼そのものではなく依頼の保存済みコピーを指定している場合、`creationDescription` は自分で書く短い要約である。作成処理はそのコピーから元のテキストを読むので、依頼を提案に貼り付けてはならない。レポートのみ/タスクなしの提案の場合は、承認前に根拠のある説明を導き出し、ディスパッチの `--request` の id と、その説明を1つの POSIX シングルクォート済み argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する（スキルの依頼ファイルの規則が挙げる文字を含む場合は依頼ファイルを経由する: **Words that would ask go to `next` in a file**、および `execute_pwsh` の場合は **Free text through `execute_pwsh`** の依頼の項目）。id は作業をそのゲートに結び付け、1回だけ有効である。返された作成の print には、「Acting on a directive」の記述どおりに対応する。scope のみの作成は決して実行しない。

**実行中の再構成（ワークフローが RUNNING の場合）:** 承認されたら、指定された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省く。このコマンドは厳格に検証し（必須入力が欠ける場合は拒否する）、カーソルより先の PENDING ステージだけを切り替え、派生する状態フィールドを再構築し、RECOMPOSED を監査ログに記録する。状態ファイルのサフィックスを手で編集してはならない。

コンポーザーが提案し、人間が決定し、決定的な検証器が守る。あなたが散文で即興のグリッドを作ることは決してなく、コンポーザーがワークフローを前進させることも決してない。
