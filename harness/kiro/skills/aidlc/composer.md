# Composing a workflow plan (the adaptive composer)

エンジンの `print` が composer エージェントを指定したときに、これを読む: compose の依頼、`--new-scope`、`--report <path>`、"compose" と答えたコールドスタート時の compose の申し出、またはワークフロー実行中の compose の依頼である。これはこのファイルの隣にある `SKILL.md` を補うものであり、そちらも引き続き適用される。

エンジンは、スコープの確認の代わりに COMPOSER DISPATCH を指定することがある: `/aidlc compose "<task>"`、`--new-scope`、`--report <path>` のとき、または人間がコールドスタート時の compose の申し出に "compose" と答えたとき、`next` は composer エージェントを指定するメッセージを持つ `print` を出力する。他のディスパッチと同様に扱う: メッセージの指示をタスクとして、`subagent` ツール経由で `aidlc-composer-agent` に委任する（エージェント設定が自身のペルソナを読み込む）。composer は読み取り専用の `detect` スキャンを実行し、5つのエントロピー要素（インテントの曖昧さ、構造の不確実性、検証のエントロピー、リスク、未解決の前提）を見積もり、構造化された提案を返す: `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }`。すべての SKIP に理由が付き、さらに事前に描画された2つの markdown 表（帯域付きの ARS スコア、理由付きのステージごとの判断）が付く。

その提案を人間に「短い」申し出として表示し、その後 `question-rendering.md` に従って承認/編集/却下のゲートを提示する（Approve / Edit the plan / Reject。カスタム計画には2つ目の承認が加わるので、そのゲートは Approve / Approve and save as scope / Edit the plan / Reject となる）。**申し出は短く保つ: 平易な推奨と計画を示し、詳細は求められたときに示す。** まず、自分の言葉で2〜3文: この変更がどのような種類のものに見えるか、それゆえどの程度のプロセスを勧めるか、そして平易な言葉でのステージ一覧（"a short run: design, build, test"）。次に、計画と、提案の `summary` にある検証器の `shown` と `gates` の数（Initialization 以降のステージ。進捗行が使う数）を1行で示す。手で数え直してはならず、平易な言葉で: "Plan: <scopeName>, <N> stages, <G> approval questions"（カスタム計画では "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` が `skipped_inputs`（この計画がスキップする各ステージと、残すステージのうちそれが作るものを使うもの。あれば）を持つ場合は、その後に平易な1行で一度だけ、すべてをまとめて、1つ残らず名指しして伝える: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution."。その後、以下の Guard Policy とスコープ設定の行を示し、各ステージを含めた理由・外した理由と規模見積もりの根拠となるスコアを見たいときは尋ねられる、という1行を加える。composer の `mode` は、返されたグリッドについて最終的なものである: composer は検証器の `nearest_stock` 距離に基づいて matched と custom を振り分けており、matched の提案はすでに再検証済みの標準グリッドをそのまま持っている - グリッドを自分で比較して判定を導き直してはならず、どの提案もスコープファイルを書かない。`skipped_inputs` の行を除き、composer のステージ判断表（その下にある統合に関する助言を含む）と ARS スコア表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに示す: まずステージ表、次に **"Scoring detail (advisory)"** の下にスコア表を、その `method`（codekb | fallback）の行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。利用者が尋ねない限り、チャットでスコアの構成要素を説明しない。このゲートは、ステージゲートと同様、ターンを確実に止める地点である: 沈黙を承認とみなしてはならず、明示的な承認の前にスコープデータを書いたりワークフローを作成したりしてはならない。編集の場合は、composer を再ディスパッチして変更を適用させ、検証を再実行し、サマリーとステージ判断表を作り直し、短い申し出を再提示する。編集では、ステージ、Guard Policy、スコープ設定を変更できる。編集が matched の標準グリッドを変更する、またはその Guard Policy を下げる場合、改訂された提案は**必ず** CUSTOM にならなければならず、承認が編集を運ぶ。それ以外の設定変更はルートを保ち、`creationSettings` を通じてこの作業に適用される。却下の場合は停止する（作業の実行中であれば、ディスパッチの print が次に何をするかを伝える）。人間は代わりにスコープを直接名指しできる。このハーネスでは、あなたも composer もスコープファイルを書かない: 保存はエンジンの `scope save` が行う（下記の step 2）。提案は `guardPolicy`（`strict`、`relaxed`、`off`）と1行の `guardPolicyRationale` も持つ: それを提案の独立した行として表示し（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"）、人間が承認前に切り替えられるようにする。実行中の場合は、その行を読み取り専用で表示し（再構成で反映されるのはステージのスキップと追加だけである）、経路を示す: 上げるまたは下げるよう求められたら、利用者が同時に求めたスコープ変更があればその前に、`{{INVOKE}} engine config set guard-policy <value> --message <id>` を自分で実行する（`<id>` は依頼のあったメッセージ）。利用者が求めたスコープ変更は新しいスコープ自身の既定値を運び、それ以外のスコープ変更は実行中のポリシーを保ち、そのことを1行で伝える。インテントの作成は、計画が実行されるスコープから Guard Policy を引き継ぐ: matched の計画では標準の既定値、カスタム計画では `baseScope` の既定値であり、composer の検証器はその値以下のものを選んでいる。`strict` または `relaxed` には `--guard-policy <value>` を渡し、`off` には決して渡さない（作成時にはスコープ自身の既定値が記録されるか、それより低い値が引き上げられる）。このゲートで人間が matched の計画を標準の既定値より下に切り替えた場合、それは編集である: composer がその値を持つベースの上のカスタム計画に変換するので、後から設定コマンドは実行しない。既定値より上への切り替えは計画を matched のまま保ち、作成時にそのフラグで適用される。提案は `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` がそれぞれ `on` または `off`、`review_cap` が `adversarial`、`advisory`、`none` のいずれか）と1行の `scopeSettingsRationale` も持つ: 常にもう1つの行として表示し（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"）、そこで人間が求めたことは何であれ実行する。`scopeSettings` のない matched またはカスタムの提案は、composer の振り分け済みの検証を通過していない: 検証されていない行を表示するのではなく、composer を再ディスパッチする。composer が、このマシンで `on` の値を強制的にオフにするキルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその仲間）を報告した場合は、行のその値に、ここでは強制的にオフであると記す。スコープファイルは書かれない: 計画が実行される標準スコープと異なる値は、`creationSettings` を通じてこの作業にだけ適用され、`--scope <scopeName>`（カスタム計画では `--scope <baseScope>`）の後に作成フラグとして付けられる。変更はルートを保つが、matched の計画の Guard Policy を下げる場合は例外で、composer がカスタム計画に変える。計画承認は提案が示す値を保つ: `creationSettings` 内の `plan_approval`（尋ねずにビルドするベースの上でそれを引き上げるカスタム計画）は、他の設定と同様に `--plan-approval` となり、それをオフにするのは利用者だけである。このゲートやスコープの確認の場面で、利用者が自分の言葉で計画承認のスキップを求めた場合は、ハーネスがそれを記録し、作成時にオフになるので、提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてだけ運ばれる: 各フラグは、その固定名（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）と、許可された語のいずれかと完全に一致する値（`on` または `off`。`adversarial`、`advisory`、`none`）から自分で組み立てる。キーや値がそれ以外であれば、何も適用せずに composer を再ディスパッチし、composer のテキストをコマンドに貼り付けてはならない。実行中の提案は設定の行を持たない。composer が `settingsChanges` として返す設定は、利用者が普通のチャットで求める設定（`SKILL.md` を参照）とは異なる: ゲート上の "Also suggested by the composer" の下に示し、人間が承認したときだけ適用する。こうして、利用者が求めていないものは何も変わらない。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず、再構成も実行しない。`settingsChanges` だけがある場合は、それをゲート（Approve / Reject）に示し、承認されたらディスパッチの print のとおりに適用する。両方がある場合は、Approve all / Approve stages only / Reject を提示する: Approve all では、ステージの変更と設定をフラグ（`--sensors off`、`--review none` など）として運ぶ再構成を1回だけ実行し、両方が同じ書き込みで反映されるようにする。ただし summary confirmation のオフは除く。再構成はその引き下げを拒否するためである。反映後に、`{{INVOKE}} engine config set summary-confirmation off --message <id>` を自分で実行し（`<id>` は利用者の承認）、利用者の承認を実行する。Approve stages only では、設定なしで再構成を実行する。

**Composition-moment authority.** 上記の matched/custom の標準ルーティングのルールは、front/report の構成にだけ適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す: `nearest_stock` は助言的であり、現在のスコープ/深さと凍結されたすべてのアクションは変わらず、標準グリッドやスコープレジストリへの書き込みは許されず、承認では正確な `changes.skip` / `changes.add` 配列を `recompose` に渡す。

**承認時（front/report）は、書き込みと作成を「同じ」ターンで行う - 2回目の `/aidlc` 呼び出しはしない:**

1. 先に何かを書き込むことはない: 計画はこの作業にだけ適用される。MATCHED の計画はその標準スコープ上に作成される。CUSTOM の計画はその `baseScope` 上に、型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として作成される（空でない各配列はカンマで連結し、空のものは省く。各要素は小文字、数字、ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずに composer を再ディスパッチする）。さらに、提案が `--depth <creationDepth>` を持つ場合はそれを付け（正確に `minimal`、`standard`、`comprehensive` のいずれか）、カスタム計画は `--plan-name <scopeName>` も渡す。これは利用者がゲートで見た名前である（小文字、数字、ハイフンだけからなる場合に限る。そうでなければ省く）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで人間に名前を尋ね、composer の `scopeName` を最初の選択肢として示し、step 3 の `next` コマンドに `--save-as <name>` を付ける: それが指定する作成処理が計画をそのスコープとして保存するので、その出力を伝える。名前は小文字の単語をハイフンでつないだ形で自分で組み立て、作成処理が名前は使用済みだと報告したら、別の名前を尋ね、その名前で再実行する。人間がキーワードを与えた場合だけは例外である: `--save-as` は付けず、step 3 の作成コマンドが成功した後、`next` を再実行する前に、`{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは小文字、数字、ハイフンからなる1語とする（それ以外は除外し、そのことを1行で伝える）。そうしない限り、保存されたスコープは推論の対象にならない。
3. 承認された提案の、空でない必須の `creationDescription` を使って、通常のインテント作成に進む。ディスパッチが `--request <id>` を与えている場合は、承認されたスコープでその `next --scope <name> --request <id>` コマンドを実行する（カスタム計画では、`--scope <baseScope>` の後にその `--skip` / `--add` と作成フラグを続ける）。依頼テキストを付け足したり組み立て直したりしない。タスクに基づく `creationDescription` は、引き続き元の依頼と一字一句同じでなければならない。ディスパッチが依頼を運ぶ代わりに依頼の保存済みコピーを指定している場合、`creationDescription` はあなたが書く短い要約である: 作成処理はそのコピーから元のテキストを読むので、依頼を提案に貼り付けてはならない。レポートのみ/タスクなしの提案では、承認の前に根拠のある説明を導き、ディスパッチの `--request` id と、その説明を1つの POSIX シングルクォートの argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する。id は作業をそのゲートに結び付け、一度だけ有効である。返された作成の print には、"Acting on a directive" が述べるとおりに正確に従う。スコープのみの作成は決して実行しない。

**In-flight recompose（ワークフローが実行中の場合）:** 承認されたら、指定された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省く。これは厳密に検証し（必須の入力が欠ける場合は拒否する）、カーソルより先の PENDING のステージだけを切り替え、導出される状態フィールドを再構築し、RECOMPOSED を監査に記録する - 状態ファイルのサフィックスを手で編集してはならない。

composer が提案し、人間が決め、決定的な検証器が守る。あなたが散文でグリッドを即興することは決してなく、composer がワークフローを進めることも決してない。
