# Composing a workflow plan (the adaptive composer)

エンジンの `print` がコンポーザーエージェントを指名したときにこのファイルを読む。対象は、compose 要求、`--new-scope`、`--report <path>`、コールドスタート時の compose の提案に "compose" と答えた場合、またはワークフロー実行中の compose 要求である。このファイルは同じ場所にある `SKILL.md` を補完するものであり、そちらも引き続き適用される。

エンジンはスコープ確認の代わりに COMPOSER DISPATCH を指名することがある。`$aidlc compose "<task>"`、`--new-scope`、`--report <path>` のとき、または人間がコールドスタート時の compose の提案に "compose" と答えたとき、`next` はコンポーザーエージェントを指名するメッセージを含む `print` を出力する。これは他のディスパッチと同様に扱う。メッセージの指示をタスクとして `aidlc-composer-agent` ロールを起動する（ペルソナはハーネスが解決するので、プロンプトに注入しない）。待機ツールが受け付ける最長のタイムアウトで、1 回の待機呼び出しで完了を待つ。待機がタイムアウトしてコンポーザーがまだ実行中なら、もう一度待つ。コンポーザーが提案を返さずに終了した場合は、提案を求めるメッセージを 1 通送り、それも失敗したら利用者に伝える。短い待機でポーリングしてはならない。待機のたびに利用者が読む行が出力されるからである。コンポーザーは読み取り専用の `detect` スキャンを実行し、5 つのエントロピー要素（インテントの曖昧さ、構造的不確実性、検証エントロピー、リスク、未解決の前提）を見積もり、構造化された提案 `{ mode: matched|custom, scopeName, ars{...}, arsRationale, grid, rationale[], summary }` を返す。提案にはすべての SKIP の理由と、事前にレンダリングされた 2 つの Markdown 表（バンド付きの ARS スコア表、理由付きのステージごとの判断表）が含まれる。

その提案を人間に「短い提案」としてレンダリングし、続けて `question-rendering.md` に従って承認/編集/却下のゲートを提示する（使える場合は `request_user_input`、使えない場合は番号付きの散文。選択肢は Approve / Edit the plan / Reject。カスタムプランでは 2 つ目の承認が加わり、ゲートは Approve / Approve and save as scope / Edit the plan / Reject の 4 択になる。これは `request_user_input` が受け付ける数を超えるので、このゲートは 1 通のメッセージ内で番号付きの散文（1〜4）としてレンダリングし、複数の呼び出しに分割してはならない。返答は番号でも言葉でも読み取る）。**提案は短く保つ。素直な推奨とプランだけを示し、詳細は求められたときに出す。** まず、自分の言葉で 2〜3 文を書く。この変更がどんな種類のものに見えるか、したがってどの程度のプロセスを勧めるか、そしてステージ一覧を平易な言葉で（"a short run: design, build, test"）。次に、プランと、検証器の `shown` と `gates` の数値（Initialization 以降のステージ数で、進捗行が使う数）を 1 行で示す。数値は提案の `summary` から取り、決して手で数え直さない。平易な言葉で "Plan: <scopeName>, <N> stages, <G> approval questions" と書く（カスタムプランなら "A custom plan based on <baseScope>, <N> stages, <G> approval questions"）。`summary` に `skipped_inputs`（このプランがスキップする各ステージと、残すステージのうちそれが作るものを使うステージ）が含まれる場合は、その直後に平易な 1 行で、すべてをまとめて一度だけ、漏れなく名前を挙げて伝える: "This plan skips Units Generation, which Contract Design, Functional Design and Code Generation use, and Deployment Execution." その後に、下記の Guard Policy 行とスコープ設定行を置き、各ステージを含める/外す理由や規模見積もりの根拠となるスコアを見たいときは尋ねられる、と 1 行で伝える。コンポーザーの `mode` は、返されたグリッドについて最終的なものである。コンポーザーは検証器の `nearest_stock` 距離に基づいて matched と custom を振り分けており、matched の提案には再検証済みの既製グリッドがそのまま含まれている。グリッドを自分で比較して判定を導き直してはならず、どの提案もスコープファイルを書き込まない。`skipped_inputs` の行を除き、コンポーザーのステージ判断表（その下にある fold の注意事項を含む）と ARS スコア表は、利用者が求めるまで画面に出さない。求められたら、返されたとおりに示す。まずステージ表、次に **"Scoring detail (advisory)"** の下にスコア表を、その `method`（codekb | fallback）行と `arsRationale` とともに示す。再計算したり、散文にまとめたり、削ったりしてはならない。ユーザーに求められない限り、スコアリングの要素をチャットで説明しない。このゲートはステージのゲートと同じく厳格なターン停止点である。沈黙を承認とみなしてはならず、明示的な承認の前にスコープデータを書き込んだりワークフローを作成したりしてはならない。編集の場合は、コンポーザーを再ディスパッチして変更を適用させ、検証を再実行し、サマリーとステージ判断表を作り直し、短い提案を再提示する。編集で変更できるのは、ステージ、Guard Policy、スコープ設定である。編集が matched の既製グリッドを変更するか、その Guard Policy を下げる場合、修正後の提案は必ず CUSTOM にしなければならず、そうすることで承認が編集を引き継ぐ。それ以外の設定変更は振り分けを維持し、`creationSettings` を通じてこの作業にのみ適用される。却下の場合は停止する（作業の実行中は、ディスパッチの print が次に何をするかを示す）。人間は代わりにスコープを直接指定できる。（非対話の単発 `codex exec` 呼び出しは実行途中でゲートに答えられないため、承認が必要な compose は対話セッションでのみ完了する。）提案には `guardPolicy`（`strict`、`relaxed`、`off`）と 1 行の `guardPolicyRationale` も含まれる。これを提案の独立した行としてレンダリングし（"Guard Policy: relaxed - a spike moves fast; a changed input is recorded and announced, not re-approved"）、人間が承認前に切り替えられるようにする。実行中は、この行を読み取り専用でレンダリングし（再構成で反映されるのはステージのスキップと追加だけ）、変更手段を示す。上げ下げを求められたら、`{{INVOKE}} engine config set guard-policy <value> --message <id>` を自分で実行する。`<id>` は利用者が依頼したメッセージで、利用者が同時に求めたスコープ変更よりも先に実行する。利用者が求めたスコープ変更には新しいスコープ自身の既定値が伴い、それ以外のスコープ変更は実行中のポリシーを維持し、そのことを 1 行で伝える。インテント作成時の Guard Policy は、プランが実行されるスコープから引き継ぐ。matched プランなら既製スコープの既定値、カスタムプランならその `baseScope` の既定値であり、コンポーザーの検証器はその値以下のものを選んでいる。`strict` または `relaxed` の場合は `--guard-policy <value>` を渡し、`off` の場合は決して渡さない（作成時にはスコープ自身の既定値が記録されるか、より低い値が引き上げられる）。このゲートで人間が matched プランを既製の既定値より下に切り替えた場合、それは編集である。コンポーザーはその値を持つベースの上でカスタムプランに変換するので、後から setter を実行することはない。既定値より上への切り替えはプランを matched のまま維持し、作成時にそのフラグで適用される。コンポーザーが実行中のインテントの Guard Policy を変更することは決してない。提案には `scopeSettings`（`sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators` はそれぞれ `on` または `off`、`review_cap` は `adversarial`、`advisory`、`none` のいずれか）と 1 行の `scopeSettingsRationale` も含まれる。これは必ずもう 1 行としてレンダリングし（"Scope settings: sensors on, learnings off, summary confirmation off, plan approval on, collaborators off, reviews advisory - a one-off fix with clear answers"）、人間がそこで求めたことは何であれ実行する。`scopeSettings` を持たない matched またはカスタムの提案は、コンポーザーの振り分け済み検証を通過していない。コンポーザーが検証していない行をレンダリングせず、コンポーザーを再ディスパッチする。コンポーザーが、このマシンでキルスイッチ（`AIDLC_DISABLE_SENSORS=1` とその同類）によって `on` の値が強制的にオフになっていると報告した場合は、行の中でその値を「ここでは強制オフ」と示す。スコープファイルは書き込まれない。プランが実行される既製スコープと異なる値は、この作業にのみ `creationSettings` を通じて適用され、`--scope <scopeName>` の後ろに作成フラグとして付けられる（カスタムプランなら `--scope <baseScope>`）。変更は振り分けを維持する。ただし matched プランの Guard Policy を下げる場合は例外で、コンポーザーがカスタムプランに変換する。プラン承認は提案が示す値を保つ。`creationSettings` にある `plan_approval`（尋ねずにビルドするベースの上でそれを引き上げるカスタムプラン）は、他の設定と同様に `--plan-approval` になり、それをオフにできるのは利用者だけである。このゲートやスコープ確認で、利用者が自分の言葉でプラン承認のスキップを求めた場合は、ハーネスがそれを記録し、作成時にオフになる。したがって提案はそのままにし、`--plan-approval` フラグは渡さない。設定は型付きの値（`creationSettings`、`settingsChanges`）としてのみ受け渡す。各フラグは固定の名前から自分で組み立てる（`sensors` は `--sensors`、`learnings` は `--learnings`、`summary_confirmation` は `--summary-confirmation`、`plan_approval` は `--plan-approval`、`collaborators` は `--collaborators`、`review` は `--review`）。値は許可された語のいずれかと完全に一致しなければならない（`on` または `off`、`adversarial`、`advisory`、`none`）。キーや値がそれ以外なら何も適用せずにコンポーザーを再ディスパッチし、コンポーザーのテキストをコマンドに貼り付けてはならない。実行中の提案には設定行がない。コンポーザーが `settingsChanges` として返す設定は、利用者が普通のチャットで求めた設定（`SKILL.md` を参照）とは別物である。ゲート上の "Also suggested by the composer" の下に示し、人間が承認した場合にのみ適用する。そうすれば利用者が求めていないものは何も変わらない。返された `changes.skip` と `changes.add` がどちらも空で `settingsChanges` もない場合は、ゲートを提示せず、再構成も実行しない。`settingsChanges` だけがある場合は、それをゲートで提示し（Approve / Reject）、承認されたらディスパッチの print の指示どおりに適用する。両方がある場合は Approve all / Approve stages only / Reject を提示する。Approve all では、ステージの変更と設定をフラグ（`--sensors off`、`--review none` など）として持つ再構成を 1 回だけ実行し、両方を同じ書き込みで反映させる。ただし summary confirmation のオフは除外する。再構成はその引き下げを拒否するからである。再構成が反映された後、`{{INVOKE}} engine config set summary-confirmation off --message <id>` を自分で実行する（`<id>` は利用者の承認メッセージ）。これで利用者の承認が実行される。Approve stages only では設定なしで再構成を実行する。

**Composition-moment authority（構成時点の権限）。** 上記の matched/custom の既製振り分けルールは、フロント/レポートの構成にのみ適用される。実行中のディスパッチは代わりに `{ mode: in-flight, scopeName: <current>, grid: <preserved full effective grid>, changes: { skip: [...], add: [...] } }` を返す。`nearest_stock` は参考情報にすぎず、現在のスコープ/深さと凍結済みのすべてのアクションは変わらず、既製グリッドやスコープレジストリへの書き込みは許されない。承認時には、`changes.skip` / `changes.add` の配列をそのまま `recompose` に渡す。

**承認時（フロント/レポート）は、書き込みと作成を同じターンで実行する。`$aidlc` を 2 回目に呼び出してはならない:**

1. 先に書き込むものは何もない。プランはこの作業にのみ適用される。MATCHED プランはその既製スコープ上で作成される。CUSTOM プランはその `baseScope` 上で、型付きの `changes` を `--skip <changes.skip> --add <changes.add>` として付けて作成される（空でない各配列はカンマで連結し、空の配列は省く。各要素は小文字・数字・ハイフンからなるステージ slug でなければならず、それ以外のものがあれば何も適用せずにコンポーザーを再ディスパッチする）。提案に `--depth <creationDepth>` がある場合はそれも付け（値は `minimal`、`standard`、`comprehensive` のいずれかと完全一致）、カスタムプランでは `--plan-name <scopeName>`（利用者がゲートで見た名前）も渡す（小文字・数字・ハイフンからなる場合のみ。それ以外なら省く）。
2. **Approve and save as scope** の場合は、ゲートと同じ質問ツールで人間に名前を尋ね、コンポーザーの `scopeName` を最初の選択肢として提示し、手順 3 の `next` コマンドに `--save-as <name>` を付ける。それが指定する作成処理がプランをそのスコープとして保存するので、その出力を伝える。名前は小文字の単語をハイフンで連結して自分で組み立て、作成処理がその名前は使用済みだと報告したら、別の名前を尋ねてその名前で再実行する。唯一の例外は人間がキーワードを与えた場合である。そのときは `--save-as` を付けず、手順 3 の作成コマンドが成功した後、`next` を再実行する前に `{{INVOKE}} engine scope save --name <name> --keywords <word,...>` を実行する。各キーワードは小文字・数字・ハイフンからなる 1 語とする（それ以外は除外し、そのことを 1 行で伝える）。保存したスコープは、これをしないと推定の対象にならない。
3. 承認された提案の、空白でない必須の `creationDescription` を使って、通常のインテント作成に進む。ディスパッチが `--request <id>` を指定している場合は、承認されたスコープでその `next --scope <name> --request <id>` コマンドを実行する（カスタムプランなら `--scope <baseScope>` の後ろに `--skip` / `--add` と作成フラグを付ける）。要求テキストを追記したり再構成したりしてはならない。タスク起点の `creationDescription` は、引き続き元の要求と一字一句一致しなければならない。ディスパッチが要求の本文を持たず、その保存済みコピーを指定している場合、`creationDescription` は自分で書く短い要約である。作成処理は元のテキストをそのコピーから読むので、要求を提案に貼り付けてはならない。レポートのみ/タスクなしの提案では、承認前に根拠のある説明文を導き出し、ディスパッチの `--request` の id と、その説明文を POSIX のシングルクォートで囲んだ 1 つの argv 値として、`{{INVOKE}} engine orchestrate next --scope <name> --request <id> -- <shell-safe creationDescription argv>` を実行する。id は作業をそのゲートに結び付けるもので、一度だけ有効である。返された作成の print には、"Acting on a directive" の説明どおりに対応する。スコープのみの作成は決して実行しない。

**実行中の再構成（ワークフローが RUNNING のとき）:** 承認されたら、指定された `recompose [--skip <slugs>] [--add <slugs>] [approved setting flags --message <id>]` コマンドを実行する。空でないリストはカンマで連結し、リストが空のフラグは省く。このコマンドは厳格に検証し（必須入力が欠けると拒否する）、カーソルより先にある PENDING のステージだけを切り替え、派生状態フィールドを作り直し、RECOMPOSED を監査ログに記録する。状態ファイルのサフィックスを手で編集してはならない。

コンポーザーが提案し、人間が決定し、決定論的な検証器が守る。グリッドを散文の中で即興で作ってはならず、コンポーザーがワークフローを前進させることも決してない。
